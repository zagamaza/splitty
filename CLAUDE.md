# Splitty / Splitor

В сторе приложение называется **Splitor**, в репозитории и bundle id — `splitty`.
Источник правды для витрин обоих магазинов — каталог `metadata/`, а не веб-интерфейсы
(см. `metadata/README.md`). Правка в консоли переживёт ровно до следующей заливки.

## Обязательное правило: клиентская фича покрывается аналитикой

Любая новая или изменённая user-facing фича на iOS и Android **обязана** слать
события в ключевых точках: показ, попытка, исход. Фича без этого считается
незавершённой — тем же правилом, что и «без тестов».

Порядок именно такой, и он не формальность:

1. **Сначала** событие описывается в [`docs/analytics-events.md`](docs/analytics-events.md) —
   имя, когда стреляет, параметры и их **закрытые** множества значений.
2. **Потом** имя попадает в белый список `internal/analytics/events.go`.
   Контракт-тест рядом читает документ и сверяет с кодом: разошлись — тест
   красный. Незнакомое имя сервер отбивает, а не пишет.
3. **Потом** событие добавляется в `AnalyticsEvent` на **обеих** платформах
   (iOS `Core/Analytics.swift`, Android `core/analytics/AnalyticsEvent.kt`) и
   инструментируется через типизированный вызов, а не строкой на месте.

Почему так строго: имя события — проводной контракт между тремя сторонами.
Опечатка в нём ничего не роняет — она молча уводит шаг воронки в никуда, и
видно это будет только по неправильному числу через месяц.

**Что в событиях не бывает:** сумм, названий тус, описаний расходов, имён — вообще
никакого содержимого. Только имя события и пометки из закрытых списков. Иначе
агрегат нельзя сгруппировать, а само событие превращается в утечку.

**Границы шага собираются сразу, даже когда считать по ним ещё рано.** Низкий
объём запрещает показывать проценты, но не запрещает диагностику, а не собранное
вчера завтра не появится. У каждого шага, про который когда-нибудь захочется
спросить «сколько дошло», должны быть показ, попытка и исход — не только успех.

**Паритет платформ проверяется глазами, а не на слово.** Событие, объявленное в
контракте и не позванное на одном из клиентов, выглядит работающей
инструментовкой и молчит:

```
grep -rho "Analytics.shared.track(\.[a-zA-Z]*" ios/Splitty --include="*.swift" | sort -u
grep -rho "AnalyticsEvent\.[A-Za-z]*" android/app/src/main/java --include="*.kt" | sort -u
```

Списки обязаны совпадать. Отдельно проверять, что объявленный хелпер где-то
**позван**: мёртвый `fun trackX()` со стороны неотличим от работающего.

**После включения сбора** — обновить декларации магазинов, см.
[`docs/store-privacy-analytics.md`](docs/store-privacy-analytics.md). Расхождение
между тем, что приложение делает, и тем, что заявлено, ловится на ревью.

## Релиз iOS: всё делается по API, браузер не нужен

Отправка в ревью не требует ни входа в App Store Connect, ни двухфакторного кода.
Ключ уже есть, и им закрывается весь путь — смена версии, привязка сборки, submit.

```
ключ    ~/.appstoreconnect/private_keys/AuthKey_T6PMYHX4T7.p8
key id  T6PMYHX4T7
issuer  a30d44ef-0dc4-4c01-bb7b-7235968f61f8
app id  6787746052   (com.zagir.splitty)
team    K8922Y6R3M
```

Те же значения лежат в `Makefile` (`ASC_KEY`, `ASC_ISSUER`, `ASC_P8`).

**Порядок:**

1. Поднять версию в `ios/project.yml` (`CFBundleShortVersionString`, `CFBundleVersion`),
   затем `xcodegen generate`.
2. `make ios-publish` — архив, экспорт, загрузка через `altool`. Ждать
   `UPLOAD SUCCEEDED`; сборка появляется в API за пару минут и должна дойти до
   `processingState: VALID`.
3. Дальше — App Store Connect API (JWT ES256, `aud: appstoreconnect-v1`, `kid` = key id):
   - `GET /v1/apps/{appId}/appStoreVersions` — найти запись версии;
   - `PATCH /v1/appStoreVersions/{id}` — **номер версии обязан совпадать с
     `CFBundleShortVersionString` сборки**, иначе сборку к ней не привязать;
   - `PATCH /v1/appStoreVersions/{id}/relationships/build` — привязать сборку;
   - `GET /v1/reviewSubmissions?filter[app]={appId}` — после отказа заявка остаётся
     жить в состоянии `UNRESOLVED_ISSUES`; **новую создавать не нужно**, отправляется
     повторно та же;
   - `PATCH /v1/reviewSubmissions/{id}` с `attributes.submitted = true`.

**Грабли:** сразу после привязки сборки submit отвечает `409 STATE_ERROR` —
«Version is not ready to be submitted yet, please try again later». Если версия
только что привязана — помогает повтор через минуту. Но если в заявке лежит
**отклонённый** пункт, повтор не поможет никогда: 409 будет вечно, и заменить
пункт через API тоже нельзя. Отклонённую заявку переотправляют только из Console.

## Отклонённая заявка: как переотправить

API тут бессилен. Порядок в Console:

1. Страница версии → кнопка **Update Review**. Пункт `App Version` переходит из
   `Rejected` в `Ready for Review`.
2. Страница заявки (App Review → нужная заявка) → кнопка **Resubmit to App Review**
   становится активной только после шага 1.

Подписки прикреплять вручную не надо: они уже лежат в той же заявке отдельными
пунктами (группа + каждая подписка). `asc web review subscriptions list` при этом
врёт, показывая `attachedCount: 0` — смотреть надо на страницу заявки.

## Текст отказа ревьюера

Публичный API его не отдаёт, `aso-mcp` (`connect_*`) тоже — они только про
метаданные витрины. Достаётся через веб-сессию Apple:

```
asc web auth login --apple-id <apple id>     # пароль и 2FA вводит человек
asc web review show --app 6787746052
```

## CLI `asc`

Профиль для Splitty заведён (`asc auth login --name splitty`, ключ T6PMYHX4T7) и
стоит по умолчанию. Перед работой по duahabit — `asc auth switch --name habitvibe`,
иначе команды пойдут не в то приложение.

Полезное: `asc validate --app 6787746052 --version 1.8 --platform IOS` — полный
чеклист готовности, `asc status --app 6787746052` — состояние конвейера одной
строкой. Скиллы `asc-*` лежат в `.claude/skills/` основного репозитория.

## Первая версия приложения: что нельзя и что забывают

- **«Что нового» править нельзя.** API отвечает `Attribute 'whatsNew' cannot be
  edited at this time`, потому что у первого релиза этого поля не существует.
  `asc validate` всё равно ругается «what's new is empty» — это ложная тревога.
- **App Availability нужно завести руками.** Публичный API умеет только менять
  существующую запись, а её нет. Console → Pricing and Availability →
  **Set Up Availability**. Без этого `asc validate` держит блокирующую ошибку
  `availability.missing`, и релиз не выйдет даже после одобрения.

## Guideline 3.1.2(c): подписки

Отказ 03.09.2026 был ровно про это. Apple требует, чтобы **и в описании в App Store,
и на экране покупки** были: название подписки, срок, цена и рабочие ссылки на
Terms of Use (EULA) и Privacy Policy. Ссылка на политику в поле App Store Connect
не засчитывается за ссылку на условия.

В описании (все пять локалей) в конце лежит блок `SPLITOR PLUS` с этими данными,
условия — https://splitor.zagirnur.dev/terms, политика —
https://splitor.zagirnur.dev/privacy. Там же не должно быть фразы «приложение
бесплатное» без оговорки: при живой подписке это отдельный повод для отказа.
