# Splitty REST API — контракт v2

REST API поверх существующих сервисов (`internal/service`, `internal/repository`) для мобильных клиентов.
Реализация — пакет `internal/rest`. Сервер слушает адрес из env `LISTEN` (дефолт `localhost:7171`).

## Общие правила

- Базовый префикс: `/api/v1`.
- Формат: JSON, UTF-8. Даты — RFC3339 (`2026-07-05T12:00:00Z`).
- Деньги: **на границе API — целые единицы валюты комнаты**, тип `int` (копеек/центов нет). В Mongo доли получателей
  хранятся как в модели develop (`recipients_with_sum`, float64), значения для API всегда
  приводятся к целым.
- **Валюта комнаты**: у каждой комнаты одна валюта (`bson "currency"`, меняется ботом и REST).
  Поддерживаемые коды — справочник `api.Currencies` (`RUB ₽ 🇷🇺`, `USD $ 🇺🇸`, `EUR € 🇪🇺`, `IDR Rp 🇮🇩`, `KZT ₸ 🇰🇿`, `UZS сум 🇺🇿`),
  выдаётся эндпоинтом `GET /currencies`. Пустая валюта в базе (комната до выбора) на границе API
  всегда отдаётся историческим дефолтом **`RUB`**. Суммы в разных валютах **не складываются** —
  агрегаты по нескольким комнатам отдаются с разбивкой по валютам.
- Операция делится одним из двух способов (`splitType`):
  - `equally` — поровну по **каноническому правилу деления** (единое для сервера и всех клиентов):
    для операции с суммой `S` (целые рубли) и `n` получателями **в порядке массива `recipients`**:
    `base = S / n` (целочисленно), `r = S % n`; получатель с индексом `i` платит `base + 1`
    при `i < r`, иначе `base`. Сумма долей всегда равна `S`.
  - `by_exact_amount` — точными суммами: доля каждого получателя задаётся явно,
    сервер валидирует `Σ долей == S` (`400` при расхождении).
  
  Баланс: донору `+S`, каждому получателю `−его доля`.
- **Легаси-операции** (созданные в эпоху master-2021, в базе нет `recipients_with_sum` и `status`):
  сервер при чтении и при расчёте долгов **синтезирует** доли канонически (поровну, остаток
  по рублю первым получателям в порядке легаси-массива `recipients`) и трактует их как активные.
  База при этом не мутируется.
- Черновики бота (`status: draft`) и архивные версии отредактированных операций (`status: archive`)
  для REST невидимы: не отдаются, не редактируются и не участвуют в долгах/статистике.
- **«Неисчислимые» комнаты**: на легаси-данных старых версий бота балансы комнаты могут
  не сходиться (`recipients_with_sum` ≠ `sum` операции, получатели вне `members` и т.п.) —
  `service.GetRoomDebts` возвращает ошибку «cannot calculate debts». REST такие комнаты
  **не 500-ит, а изящно деградирует** (`internal/rest`: `roomDebtsSafe`): комната остаётся
  видимой (операции, участники, траты, валюта), но `debts: []`, `myBalance: 0` и в DTO
  комнаты появляется флаг **`debtsUnavailable: true`** (omitempty; клиент может показать
  бейдж «долги не считаются»). В `/friends` вклад такой комнаты пропускается, погашения
  в ней отклоняются `409 conflict`. Математика не «чинится» — бот на этих комнатах
  ошибается так же; в лог пишется однострочный warn с id комнаты.
- У операций, созданных ботом с делением поровну, в Mongo лежат **дробные** float-доли
  (`100/3 = 33.33…`); API отдаёт канонические целые доли, пересчитанные из `sum`
  и порядка массива получателей.
- ID пользователя — Telegram user id (`int`). ID комнаты/операции — hex `primitive.ObjectID` (строка).
- Аутентификация: `Authorization: Bearer <JWT>` для всех эндпоинтов, кроме `/auth/*` и `/health`.
- JWT: HS256, секрет из env `API_JWT_SECRET`; claims: `sub` = строка userId, `iat`, `exp` (90 дней, обязателен).
- Лимит тела запроса: **1 МБ** для всех эндпоинтов (включая неаутентифицированные `/auth/*`); превышение — `413 too_large`.
- Ошибки: HTTP-код + тело `{"error": {"code": "<snake_case>", "message": "<человекочитаемо>"}}`.
  Коды: `400 validation`, `401 unauthorized`, `403 forbidden`, `404 not_found`, `409 conflict`, `413 too_large`, `500 internal`;
  у `POST /auth/code` дополнительно `401 invalid_code`.

## Конфигурация (env)

| Переменная      | Дефолт            | Смысл                                            |
|-----------------|-------------------|--------------------------------------------------|
| `LISTEN`        | `localhost:7171`  | адрес HTTP-сервера REST API                      |
| `API_JWT_SECRET`| — (**обязательна**) | секрет подписи JWT; без него сервер **не стартует**. Исключение: при `API_DEV_AUTH=true` пустой секрет заменяется случайным эфемерным (все токены протухают при рестарте) |
| `API_DEV_AUTH`  | `false`           | включает `POST /auth/dev` (только для разработки; при включении сервер пишет громкое предупреждение в лог)|
| `GEMINI_API_KEY`| `""`              | ключ Google Gemini для AI-распознавания расхода. Пустой → эндпоинт `/operations/parse` отдаёт `503`, остальной сервер работает как раньше |
| `GEMINI_MODEL`  | `gemini-2.0-flash`| модель Gemini для распознавания |
| `AI_PARSE_RATE_PER_MIN` | `5`       | лимит запросов `/parse` на пользователя в минуту |
| `AI_PARSE_DAILY_QUOTA`  | `50`      | суточная квота запросов `/parse` на пользователя |
| `AI_MAX_BODY_BYTES`     | `15728640` (15 МБ) | общий лимит тела `/parse` (отдельно от глобального 1 МБ) |

Бот становится **опциональным**: если Telegram API не инициализировался (пустой/битый `TG_TOKEN`),
приложение пишет warning и продолжает работать только с REST API. REST-сервер и бот работают параллельно
(бот — `app.Do(ctx)`, сервер — в отдельной горутине, graceful shutdown через `closer`).

## DTO

```jsonc
// User
{"id": 123, "username": "zagir", "displayName": "Загир"}

// Me (профиль текущего пользователя)
{"id": 123, "username": "zagir", "displayName": "Загир", "lang": "ru", "notificationOn": true}

// Debt — debtor должен lender'у sum
{"debtor": User, "lender": User, "sum": 500}

// OperationRecipient — доля получателя в целых рублях:
// для equally — каноническая вычисленная, для by_exact_amount — хранимая
{"user": User, "sum": 400}

// Operation
{
  "id": "65a...f", "description": "Ужин", "sum": 1200,
  "isDebtRepayment": false,
  "splitType": "equally",    // "equally" | "by_exact_amount"; у погашений отсутствует
  "donor": User,             // кто заплатил
  "recipients": [OperationRecipient],  // доли получателей, Σ sum долей == sum операции
  "createdAt": "2026-07-05T12:00:00Z",
  "files": [{"type": "image", "fileId": "AgAC..."}],  // может быть пустым/отсутствовать
  "items": [OperationItem],  // детализация по позициям чека — ТОЛЬКО у itemized-операций
                             // (AI-распознанных); отсутствует/nil у обычных. Плоские
                             // recipients выше — источник долгов, items — «зачем так вышло»
  "clientOpId": "3b2f1c9e-…"  // клиентский идемпотентный ключ (см. «Идемпотентность создания»);
                              // присутствует только если операция создана через REST с ним
}

// OperationItem — позиция чека в ответе (read-path). Отдаётся в Operation.items.
{
  "name": "Пицца",
  "price": 1200,          // ВСЕГДА суммарная стоимость строки (не цена единицы)
  "qty": 2,               // только для отображения («×2»); в делёж НЕ входит
  "shares": [ItemShare],  // доли участников по позиции (у сборов пусто, omitempty)
  "kind": "item",         // "item" | "surcharge" (сервисный сбор/доставка)
  "split": "proportional",// только у surcharge: "proportional" | "equally"; иначе отсутствует
  "percent": 10           // только для показа («Сбор 10%»); в расчёте НЕ участвует (omitempty)
}

// ItemShare — доля участника в позиции
{
  "userId": 123,
  "weight": 1,    // относительный вес доли; 1 = поровну
  "amount": 500   // фикс-сумма участника (omitempty); задана → weight игнорируется
}

// Currency (запись справочника валют)
{"code": "RUB", "symbol": "₽", "flag": "🇷🇺"}

// RoomSummary (строка списка групп)
{
  "id": "65a...f", "name": "Сплит по Стамбулу", "createdAt": "...",
  "isArchived": false,
  "currency": "RUB",     // валюта комнаты; пустая в базе → "RUB"
  "members": [User], "memberCount": 4,
  "totalSpent": 34000,   // сумма всех расходов комнаты (без погашений)
  "myBalance": 500,      // >0 — мне должны, <0 — я должен, 0 — расчёт
  "debtsUnavailable": true  // только у «неисчислимых» комнат (omitempty): долги
                            // не считаются на легаси-данных, myBalance отдан нулём
}

// RoomDetail (экран группы одним запросом)
{
  "id": "...", "name": "...", "createdAt": "...", "isArchived": false,
  "currency": "RUB",
  "members": [User],
  "totalSpent": 34000, "mySpent": 8500,   // mySpent — моя доля расходов
  "myBalance": 500,
  "debts": [Debt],                        // все долги комнаты
  "debtsUnavailable": true,               // только у «неисчислимых» комнат (omitempty):
                                          // debts=[] и myBalance=0, остальное — как обычно
  "operations": [Operation]               // все операции, новые первыми
}

// FriendBalance (вкладка «Друзья»)
{
  "user": User,
  // итог по каждой валюте отдельно (валюты не складываются), только ненулевые;
  // порядок — как в справочнике валют. >0 — друг должен мне, <0 — я должен другу
  "totalsByCurrency": [{"currency": "RUB", "sum": 500}, {"currency": "USD", "sum": -100}],
  "rooms": [{"roomId": "...", "roomName": "...", "currency": "RUB", "balance": 500}]  // только ненулевые
}

// ActivityItem
{"roomId": "...", "roomName": "...", "roomCurrency": "RUB", "operation": Operation}

// Statistics (дашборд комнаты; только active-расходы, погашения исключены)
{
  "currency": "RUB",
  "totalSpent": 9400,          // сумма всех расходов комнаты
  "operationCount": 12,        // число всех расходов комнаты за всё время
  "monthSpent": 9400,          // расходы текущего календарного месяца (по create_at)
  "byDay": [{"date": "2026-07-05", "sum": 9400}],        // последние 30 дней, только дни с тратами, ISO-дата, по возрастанию
  "byMonth": [{"month": "2026-02", "sum": 0}, /* … */ {"month": "2026-07", "sum": 9400}],
  // ^ последние 6 календарных месяцев включая текущий, месяцы без трат — с sum=0, "yyyy-mm", по возрастанию
  "paidByMember": [{"user": User, "sum": 4500}],         // кто платил (донор), по убыванию суммы
  "shareByMember": [{"user": User, "sum": 3133}],        // чья доля потребления (получатели), по убыванию суммы
  "topOperations": [                                     // топ-5 расходов по сумме
    {"id": "...", "description": "Ужин", "sum": 3600, "donor": User, "createdAt": "..."}
  ]
}
```

`myBalance` считается из вычисленных долгов комнаты (`OperationService.GetAllDebts`):
`sum(долги где я lender) - sum(долги где я debtor)`.

## Эндпоинты

### Auth

`POST /api/v1/auth/telegram` — вход через Telegram Login Widget.
Тело: `{"id": 123, "firstName": "…", "lastName": "…", "username": "…", "photoUrl": "…", "authDate": 1720000000, "hash": "…"}`.
Проверка подписи: HMAC-SHA256 по data-check-string с ключом `SHA256(TG_TOKEN)` (стандарт Telegram);
`authDate` не старше **10 минут** (короткое окно против replay перехваченного payload). Upsert пользователя. Ответ: `{"token": "<jwt>", "user": Me}`.
`401 unauthorized` при неверном hash; `503` если `TG_TOKEN` не задан.

`POST /api/v1/auth/code` — вход по одноразовому коду из Telegram-бота.
Код выдаёт команда **`/login`** в личном чате бота: 8 символов из алфавита без неоднозначных
символов (`ABCDEFGHJKMNPQRSTUVWXYZ23456789`), TTL **5 минут**, одноразовый
(Mongo-коллекция `login_code`; проверка и пометка `used` атомарны — `FindOneAndUpdate`).
Тело: `{"code": "ABCD2345"}`, код регистронезависим. Ответ как выше: `{"token": "<jwt>", "user": Me}`.
`400 validation` если `code` не передан; `401 invalid_code` если код не найден, просрочен,
уже использован или пользователь не существует.

`POST /api/v1/auth/dev` — вход для разработки (**только при `API_DEV_AUTH=true`**, иначе `404`).
Тело: `{"userId": 123, "displayName": "Загир", "username": "zagir"}` → upsert пользователя, ответ как выше.

### Профиль

- `GET /api/v1/me` → `Me`
- `PATCH /api/v1/me` — тело `{"displayName"?, "lang"?, "notificationOn"?}` → обновлённый `Me`.

### Комнаты (группы)

- `GET /api/v1/rooms?archived=false` → `[RoomSummary]` (сортировка: новые первыми). `archived=true` — архив.
- `POST /api/v1/rooms` — `{"name": "…"}` → `201` + `RoomDetail`. Создатель — первый участник. Имя: непустое, ≤ 100 символов.
- `GET /api/v1/rooms/{roomId}` → `RoomDetail`. `403` если пользователь не участник, `404` если нет комнаты.
- `POST /api/v1/rooms/{roomId}/join` → `RoomDetail`. Идемпотентно (повторный join — ок). Это и есть «присоединение по приглашению»: код приглашения = `roomId` (совместимо с deep-link бота `t.me/<bot>?start=room<roomId>`).
- `POST /api/v1/rooms/{roomId}/archive` → `204` (только для участника; помечает архивной только для него — `room_states.archived`).
- `POST /api/v1/rooms/{roomId}/unarchive` → `204`.
- `PUT /api/v1/rooms/{roomId}/currency` — смена валюты комнаты (общая для всех участников,
  тот же `RoomRepository.UpdateCurrency`, что у бота). Тело: `{"currency": "USD"}` → `204`.
  `400 validation` если код не из справочника; `403` если пользователь не участник; `404` если комнаты нет.

### Валюты

- `GET /api/v1/currencies` → `[Currency]` — справочник поддерживаемых валют для пикера
  в приложении, стабильный порядок: `RUB`, `USD`, `EUR`, `IDR`, `KZT`, `UZS`.

### Операции (расходы)

- `GET /api/v1/rooms/{roomId}/operations?type=all|spend|repayment` (дефолт `all`) → `[Operation]`, новые первыми.
- `POST /api/v1/rooms/{roomId}/operations` → `201` + `Operation`.
  Тело — **ровно один** из двух режимов деления (`400`, если заданы оба или ни одного):
  - поровну (`splitType: equally`):
    `{"description": "Ужин", "sum": 1200, "donorId": 123, "recipientIds": [123, 456]}` —
    сервер раскладывает доли по каноническому правилу (см. «Общие правила»): `base = S/n`,
    остаток `S % n` по рублю первым получателям **в порядке массива** `recipientIds`
    (дубликаты id схлопываются);
  - точными суммами (`splitType: by_exact_amount`):
    `{"description": "Отель", "sum": 1200, "donorId": 123, "recipientSums": [{"userId": 123, "sum": 700}, {"userId": 456, "sum": 500}]}` —
    суммы целые, `>= 1`, каждый получатель не более одного раза, `Σ sum == sum` операции (`400` при расхождении).

  Общие правила: участник комнаты может добавлять; `donorId` и все получатели — участники комнаты;
  `sum >= 1`; `description` непустое. Операция сохраняется в модели develop:
  `status=active` (у REST нет драфт-шага бота), `splitType`, `recipients_with_sum`;
  `IsDebtRepayment=false`, `CreateAt=now`, новый `ObjectID`.
  Тело может содержать опциональный `clientOpId` — см. «Идемпотентность создания»
  (повтор с тем же ключом → `200` + существующая операция вместо `201`).

  **Itemized-режим (позиции чека, `items`).** Тело может нести **опциональный** массив
  `items: [OperationItem]` (детализация из AI-распознавания, см. `POST /operations/parse`).
  Когда `items` присутствует и непуст, он становится **источником правды**:
  - сервер **сам выводит** `recipients` (доли) и `sum` из позиций (`api.DeriveShares`) и
    **игнорирует** плоские клиентские поля `sum`/`recipientIds`/`recipientSums`;
  - `splitType` результата — всегда `by_exact_amount`;
  - позиции сохраняются в операцию (`Operation.items`) и отдаются на read-path;
  - валидация: `description` непустое; `donorId` — участник комнаты; все `userId` из
    `items[].shares` — участники комнаты (иначе `400`); поле `unknown` каждой позиции
    **должно быть пустым** — при непустом `400 validation` («сначала выберите, кто такие …»);
    позиции должны раскладываться без ошибки (перебор фиксов над ценой → `400`).

  Формат `OperationItem`/`ItemShare` — см. раздел «DTO». Клиент присылает позиции в том же
  виде, что вернул `/parse` (поле `unknown` к моменту сохранения — пустое).
- `PUT /api/v1/rooms/{roomId}/operations/{operationId}` — то же тело → `Operation`.
  **Право: любой участник комнаты** (посторонним — `403`; Splitwise-семантика, автор изменения виден в Telegram-уведомлении). Погашения (`isDebtRepayment=true`) редактировать нельзя (`409 conflict`).
  `items` работает так же, как в `POST` (сервер выводит суммы). **Плоское обновление
  без `items` затирает сохранённые позиции** (`Operation.items` → `nil`): старые клиенты
  (бот, Android, старые версии iOS) редактируют itemized-операцию плоско и не разъезжаются
  с сервером — детализация просто сбрасывается, плоские суммы остаются валидными.
- `DELETE /api/v1/rooms/{roomId}/operations/{operationId}` → `204`. Право: любой участник комнаты. Погашение удалять можно (отмена платежа).

### AI-распознавание расхода (parse)

- `POST /api/v1/rooms/{roomId}/operations/parse` — распознаёт расход из **голоса**,
  **фото чека** или **текста** в структурированный черновик. **Ничего не создаёт и не хранит** —
  это чистая функция «черновик + ввод → черновик» (**stateless**): один и тот же вызов
  используется и для распознавания с нуля, и для голосовой правки (тогда передаётся
  текущий `draft`). Сохранение — обычным `POST/PUT /operations` с полем `items`.

  Тело — **`multipart/form-data`**, ровно один вид ввода (приоритет `audio → image → text`):
  - `audio` — файловая часть, `Content-Type` из allowlist: `audio/aac` (основной для iOS),
    `audio/mpeg`, `audio/mp3`, `audio/wav`, `audio/x-wav`, `audio/ogg`, `audio/flac`;
  - `image` — файловая часть, `Content-Type`: `image/jpeg` (основной), `image/png`,
    `image/webp`, `image/heic`;
  - `text` — обычное поле формы (строка);
  - `draft` — **опциональное** поле формы: JSON текущего черновика (`Draft`) для голосовой
    правки. При его наличии модель применяет дельту, не пересобирая уже проставленные доли.

  Ответ `200`:
  ```jsonc
  {
    "draft": Draft,          // обновлённый черновик (см. ниже)
    "questions": ["кто платил?", "не расслышал сумму"]  // уточняющие вопросы, omitempty
  }
  ```

  Форма черновика (транспортный контракт, тот же тип используется в `items` при сохранении):
  ```jsonc
  // Draft
  {
    "description": "Ужин",
    "sum": 4700,
    "donorId": 123,          // кто платил (omitempty; null если модель не поняла)
    "items": [DraftItem]     // позиции чека (omitempty)
  }

  // DraftItem — как OperationItem (см. «DTO»), плюс поле unknown:
  {
    "name": "Пицца", "price": 1200, "qty": 2,
    "shares": [{"userId": 123, "weight": 1, "amount": 500}],  // amount — фикс-сумма (omitempty)
    "kind": "item",          // "item" | "surcharge"
    "split": "proportional", // только surcharge: "proportional" | "equally"
    "percent": 10,           // только display (omitempty), в расчёте не участвует
    "unknown": ["саня"]      // имена, которые модель не сматчила участникам (omitempty);
                             // пользователь разрешает их в UI. Пока unknown непуст —
                             // операцию с этими items сохранить нельзя (400 на записи)
  }
  ```

  Семантика полей позиции — как у `OperationItem` (раздел «DTO»): `price` — всегда total
  строки; `qty` — только display; у `surcharge` сумма берётся из `price` (`percent` — только
  показ), доли считаются от базовых долей людей по правилу `split`.

  **Доступ и защиты:**
  - auth обязателен (`401` без токена); пользователь — участник комнаты (`403` иначе);
  - **rate-limit** на пользователя (запросов/мин + суточная квота): при превышении
    `429 rate_limited` (проверяется **до** чтения больших частей и вызова модели);
  - `503 ai_disabled` если AI выключен (не задан `GEMINI_API_KEY`);
  - лимиты тела: общий `AI_MAX_BODY_BYTES` (~15 МБ, **отдельно** от глобального 1 МБ —
    для этого пути глобальный лимит снят), покусочно `audio ≤ 3 МБ`, `image ≤ 8 МБ`,
    `draft ≤ 64 КБ`; превышение — `413 too_large`;
  - неподдерживаемый `Content-Type` части — `415 unsupported_media`;
  - `400 validation` если не передан ни один вид ввода или `draft` невалиден;
  - при ошибке модели — `502` с телом `{draft, questions}`, где `draft` — **эхо входного
    черновика** (то, что пользователь уже надиктовал, не теряется).

### Прозвища участников (aliases)

- `POST /api/v1/users/{userId}/aliases` — добавляет пользователю прозвище, чтобы AI сматчил
  его в следующий раз (нераспознанное имя из `unknown` → выбор человека → дозапись алиаса).
  Тело: `{"alias": "Саня"}` → `204 No Content`. Алиас нормализуется (`trim` + нижний регистр),
  хранится с дедупликацией (`$addToSet`).
  Право: в **свой** профиль — всегда; в чужой — только если есть **общая комната**
  с `userId` (`403 forbidden` иначе). Пустой алиас — `400 validation`.

### Долги и погашение (settle up)

- `GET /api/v1/rooms/{roomId}/debts?involving=all|me` (дефолт `all`) → `[Debt]`.
  Долги считаются расчётом develop (`service.GetRoomDebts`) по активным операциям
  (легаси-операции — с синтезированными долями, см. «Общие правила»).
  «Неисчислимая» комната (см. «Общие правила») отдаёт `200` и пустой список.
- `POST /api/v1/rooms/{roomId}/repayments` → `201` + `Operation`.
  Тело: `{"debtorId": 123, "lenderId": 456, "sum": 500}`.
  Создаёт операцию как бот develop: `IsDebtRepayment: true`, `status: active`, `Donor: debtor`,
  `recipients_with_sum: [{lender, sum}]`, без `splitType`.
  Правила: текущий пользователь — один из `debtorId`/`lenderId`; оба — участники; `sum >= 1`;
  `sum <=` текущего долга debtor→lender (`409 conflict` если больше или долга нет).
  В «неисчислимой» комнате (см. «Общие правила») долги не считаются, гасить нечего —
  `409 conflict` с сообщением «долги этой группы не считаются из-за старых данных», не `500`.
  Конкурентные погашения одного долга (mongo без транзакций) разрешаются компенсацией:
  если после вставки долг ушёл в минус, погашение откатывается и возвращается `409 conflict` —
  клиент перечитывает долги и при необходимости повторяет запрос.
  Тело может содержать опциональный `clientOpId` — см. «Идемпотентность создания»:
  повтор с тем же ключом возвращает `200` + существующее погашение **до** проверки долга
  (первая доставка долг уже погасила, иначе повтор получал бы ложный `409`).

### Идемпотентность создания (clientOpId)

Офлайн-клиенты (iOS/Android) копят операции в локальном **outbox** и досылают их при появлении
сети. Доставка «хотя бы один раз»: ответ сервера мог потеряться после успешной вставки, и повтор
того же запроса без защиты создал бы дубль расхода/погашения. Поэтому:

- `POST /rooms/{roomId}/operations` и `POST /rooms/{roomId}/repayments` принимают
  **опциональное** поле `clientOpId` — клиентский идемпотентный ключ (UUID, который клиент
  генерирует при постановке операции в outbox). Формат: ≤ 64 символов из `[A-Za-z0-9-]`,
  иначе `400 validation`. Без поля поведение прежнее (каждый POST создаёт операцию).
- Семантика: если в комнате **уже есть** операция с таким `client_op_id`, дубль не создаётся —
  возвращается **`200`** + существующая `Operation`. Первая успешная вставка отвечает **`201`**.
  Клиент трактует оба кода как успех и сопоставляет локальную запись с серверной по `clientOpId`
  (он отдаётся в `Operation`).
- Ключ уникален **в пределах комнаты** и хранится в операции (`bson client_op_id`, пустой не
  сериализуется; операции бота ключа не имеют). Тело повтора не сравнивается с существующей
  операцией — ответственность за «один ключ = одна операция» на клиенте.
- Гонки: проверка и вставка выполняются **атомарно** — одним `UpdateOne` с фильтром
  `{_id, "operations.client_op_id": {$ne: clientOpId}}` и `$push`; конкурентные повторы одного
  ключа дают ровно одну операцию (`201` победителю, `200` остальным).
- В `PUT /operations/{operationId}` поле игнорируется: хранимый ключ операции не меняется.

### Telegram-уведомления о мутациях

Успешные мутации через REST шлют участникам комнаты **те же telegram-уведомления, что и бот**
(`bot.Notifier`, тексты — ключи `scrn_notification_*`/`scrn_debt_returned_recepient` из
`conf/lang/*.ini`, язык — настройка получателя, суммы — в валюте комнаты, с inline-кнопками
«Посмотреть операцию»/«В тусу»). Набор событий — строгий паритет со сценариями бота
(`internal/bot/operation_screen.go`), ничего сверх бота не выдумано:

- `POST /operations` (создание): назначенному плательщику, если он не автор запроса —
  «назначил(а) тебя плательщиком»; каждому получателю с ненулевой долей (кроме автора) —
  «добавил(а) тебя в операцию» с его долей. Уведомлённые помечаются в `notification_sent`
  операции (как у бота). Идемпотентный **повтор** с тем же `clientOpId` не уведомляет второй раз.
- `PUT /operations/{id}` (изменение): по диффу old/new, как в боте — смена плательщика
  (обоим донорам, кроме автора), изменение названия/добавление фото (всем участникам операции),
  добавленным получателям, получателям с изменённой долей, удалённым получателям.
- `DELETE /operations/{id}` (удаление расхода): каждому получателю — «убрал(а) тебя из операции»
  (у бота удаление реализовано как «изменение, убравшее всех получателей»). Удаление
  **погашения** не уведомляет — у бота нет такого сценария/текста.
- `POST /repayments` (погашение): кредитору — «тебе был возвращён долг», если погашение создал
  должник. Если погашение подтвердил сам кредитор — никто не уведомляется (текста для должника
  у бота нет). Откатившееся компенсацией погашение (`409`) не уведомляет.

Общие правила: автор мутации никогда не уведомляется; `notificationOn` получателя уважается
(`nil` → включено; исключения — паритет с ботом: смена плательщика и возврат долга уходят без
этой проверки, как в боте). Отправка — **после успешной записи, в фоне** (ответ клиенту не ждёт
telegram), ошибки отправки только логируются. Уведомления работают только когда бот
сконфигурирован (`TG_TOKEN` задан); без бота REST работает как раньше, уведомления — no-op.

### Друзья и активность (агрегаты по всем неархивным комнатам пользователя)

- `GET /api/v1/friends` → `[FriendBalance]` — все со-участники по всем моим неархивным комнатам;
  `totalsByCurrency` — нетто по вычисленным долгам всех комнат **с разбивкой по валютам**
  (валюты не складываются; только ненулевые итоги, порядок — как в справочнике валют).
  Сортировка: сначала ненулевые (по сумме модулей итогов всех валют, убыв.), потом рассчитанные.
  Вклад «неисчислимых» комнат (см. «Общие правила») пропускается и не рушит агрегат;
  друзья из таких комнат остаются в списке (с нулевым вкладом от этих комнат).
- `GET /api/v1/activity?limit=30&offset=0` → `[ActivityItem]` — операции всех моих неархивных комнат, новые первыми.
  `limit` ограничен диапазоном 1..100 (значения сверх — клампятся), `offset >= 0`; `offset` за концом списка — пустой ответ.

### Статистика

- `GET /api/v1/rooms/{roomId}/statistics` → `Statistics` — расширенная статистика для дашборда.
  Считаются **только активные расходы** (погашения и черновики исключены), легаси-операции —
  через существующую нормализацию (`normalizedRoom`), доли получателей — канонические целые.
  - `currency` — валюта комнаты (пустая в базе → `RUB`);
  - `totalSpent` — сумма всех расходов комнаты;
  - `operationCount` — число всех расходов комнаты за всё время (погашения и черновики не считаются);
  - `monthSpent` — расходы текущего календарного месяца (по `create_at`);
  - `byDay` — траты по дням за последние 30 календарных дней (включая сегодня):
    только дни с тратами, ISO-дата `yyyy-mm-dd`, по возрастанию даты;
  - `byMonth` — траты по календарным месяцам за последние 6 месяцев (включая текущий):
    ровно 6 элементов, месяцы без трат присутствуют с `sum: 0`, формат `yyyy-mm`,
    по возрастанию месяца (по `create_at`);
  - `paidByMember` — кто сколько заплатил (доноры расходов), по убыванию суммы;
  - `shareByMember` — чья доля потребления (получатели с их долями), по убыванию суммы;
  - `topOperations` — топ-5 расходов по сумме (`id`, `description`, `sum`, `donor`, `createdAt`).

### Файлы (чеки/фото из Telegram)

- `GET /api/v1/files/{fileId}` — проксирует файл из Telegram (`getFile` + download по `file_path`).
  Доступ: аутентифицированный пользователь, у которого есть комната с операцией, содержащей этот `fileId` (`403` иначе).
  `503 unavailable` если бот не сконфигурирован.

### Служебное

- `GET /health` → `200 {"status":"ok"}` (без авторизации).

## Замечания по реализации

- Роутинг: stdlib `net/http` + `http.ServeMux` c паттернами методов (Go ≥1.22).
- JWT: `github.com/golang-jwt/jwt/v5`.
- **Авторизация — обязанность REST-слоя**: членство в комнате и авторство операции проверять в хендлерах (в сервисах проверок нет).
- Долги считать расчётом develop — `service.GetRoomDebts` — по **нормализованной копии**
  комнаты (`internal/rest`: `normalizedRoom`): легаси-операции получают синтезированные
  канонические доли, драфты/архив исключаются; база не мутируется. Алгоритм не дублировать.
- Каноническое правило деления — `api.ShareOf` (`internal/api/money.go`), общее для
  создания операций, отдачи DTO и синтеза легаси-долей.
- Все хендлеры — тонкие: парсинг → проверки прав → вызов сервиса → маппинг в DTO.
