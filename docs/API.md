# Splitty REST API — контракт v2

REST API поверх существующих сервисов (`internal/service`, `internal/repository`) для мобильных клиентов.
Реализация — пакет `internal/rest`. Сервер слушает адрес из env `LISTEN` (дефолт `localhost:7171`).

## Общие правила

- Базовый префикс: `/api/v1`.
- Формат: JSON, UTF-8. Даты — RFC3339 (`2026-07-05T12:00:00Z`).
- Деньги: **на границе API — целые единицы валюты комнаты**, тип `int` (копеек/центов нет). В Mongo доли получателей
  хранятся как в модели develop (`recipients_with_sum`, float64), значения для API всегда
  приводятся к целым.
- **Валюта комнаты**: у каждой комнаты одна валюта (`bson "currency"`, меняется ботом и REST).
  Поддерживаемые коды — справочник `api.Currencies` (`RUB ₽ 🇷🇺`, `USD $ 🇺🇸`, `EUR € 🇪🇺`, `IDR Rp 🇮🇩`, `KZT ₸ 🇰🇿`, `UZS сум 🇺🇿`),
  выдаётся эндпоинтом `GET /currencies`. Пустая валюта в базе (комната до выбора) на границе API
  всегда отдаётся историческим дефолтом **`RUB`**. Суммы в разных валютах **не складываются** —
  агрегаты по нескольким комнатам отдаются с разбивкой по валютам.
- Операция делится одним из двух способов (`splitType`):
  - `equally` — поровну по **каноническому правилу деления** (единое для сервера и всех клиентов):
    для операции с суммой `S` (целые рубли) и `n` получателями **в порядке массива `recipients`**:
    `base = S / n` (целочисленно), `r = S % n`; получатель с индексом `i` платит `base + 1`
    при `i < r`, иначе `base`. Сумма долей всегда равна `S`.
  - `by_exact_amount` — точными суммами: доля каждого получателя задаётся явно,
    сервер валидирует `Σ долей == S` (`400` при расхождении).
  
  Баланс: донору `+S`, каждому получателю `−его доля`.
- **Легаси-операции** (созданные в эпоху master-2021, в базе нет `recipients_with_sum` и `status`):
  сервер при чтении и при расчёте долгов **синтезирует** доли канонически (поровну, остаток
  по рублю первым получателям в порядке легаси-массива `recipients`) и трактует их как активные.
  База при этом не мутируется.
- Черновики бота (`status: draft`) и архивные версии отредактированных операций (`status: archive`)
  для REST невидимы: не отдаются, не редактируются и не участвуют в долгах/статистике.
- **«Неисчислимые» комнаты**: на легаси-данных старых версий бота балансы комнаты могут
  не сходиться (`recipients_with_sum` ≠ `sum` операции, получатели вне `members` и т.п.) —
  `service.GetRoomDebts` возвращает ошибку «cannot calculate debts». REST такие комнаты
  **не 500-ит, а изящно деградирует** (`internal/rest`: `roomDebtsSafe`): комната остаётся
  видимой (операции, участники, траты, валюта), но `debts: []`, `myBalance: 0` и в DTO
  комнаты появляется флаг **`debtsUnavailable: true`** (omitempty; клиент может показать
  бейдж «долги не считаются»). В `/friends` вклад такой комнаты пропускается, погашения
  в ней отклоняются `409 conflict`. Математика не «чинится» — бот на этих комнатах
  ошибается так же; в лог пишется однострочный warn с id комнаты.
- У операций, созданных ботом с делением поровну, в Mongo лежат **дробные** float-доли
  (`100/3 = 33.33…`); API отдаёт канонические целые доли, пересчитанные из `sum`
  и порядка массива получателей.
- **ID пользователя — номер Splitty** (`int`), а НЕ telegram user id. Исторически они совпадали
  (телеграм был единственным способом входа), поэтому у старых аккаунтов `_id` действительно равен
  telegram id — но у пришедших через Google/Apple telegram id нет вовсе, а `_id` выдан аллокатором
  из диапазона от `1_000_000_000_000`. Telegram-личность живёт в отдельном поле `telegram_id`
  (см. «Модель личности» в [README](../README.md)). ID комнаты/операции — hex `primitive.ObjectID` (строка).
- Аутентификация: `Authorization: Bearer <JWT>` для всех эндпоинтов, кроме `/auth/*`, `/health`,
  `/join/{roomId}` и `/.well-known/*`.
- JWT: HS256, секрет из env `API_JWT_SECRET`; claims: `sub` = строка userId, `iat`, `exp` (90 дней, обязателен).
- Лимит тела запроса: **1 МБ** для всех эндпоинтов (включая неаутентифицированные `/auth/*`); превышение — `413 too_large`.
- Ошибки: HTTP-код + тело `{"error": {"code": "<snake_case>", "message": "<человекочитаемо>"}}`.
  Коды: `400 validation`, `401 unauthorized`, `403 forbidden`, `404 not_found`, `409 conflict`, `413 too_large`, `500 internal`;
  у `POST /auth/code` дополнительно `401 invalid_code`; у внешних способов входа —
  `429 rate_limited` и `503 unavailable`; у `/me/link/*` — `409 identity_taken`,
  `409 identity_already_linked`, `409 last_identity` и `400 provider_rejected`;
  у входа по паролю — `409 email_taken`, `401 invalid_credentials`, `403 invalid_password`;
  у состава группы — `403 not_a_friend`, `409 has_operations`, `409 last_member`,
  `409 not_pending`.
- **`429 rate_limited` отдаёт не только внешний вход.** Троттлятся: `POST /auth/code` (10 попыток
  на адрес в минуту + общий бюджет неудач 100/мин на весь сервер), `POST /auth/{google|apple}`
  (20 на адрес в минуту, свой ключ у каждого), `POST /auth/{register|login}` (20 на адрес в
  минуту, свой ключ у каждого), `POST /me/password` (20 в минуту **на пользователя**),
  `POST /me/link/*` (20 в минуту **на пользователя**) и `GET /join/{roomId}` (60 на адрес в минуту).
- ⚠️ **`401 unauthorized` всегда означает «сессия Splitty мертва»** — клиенты по нему разлогинивают
  человека. Поэтому отвергнутый токен ВНЕШНЕГО провайдера на `/me/link/*` отвечает
  **`400 provider_rejected`**, а не `401`: разъехавшиеся часы или ещё не прописанный `aud` не
  должны выкидывать пользователя из живой сессии.
- ⚠️ Адрес клиента для лимитов берётся из `RemoteAddr`. `X-Forwarded-For` читается, **только** если
  задан `TRUSTED_PROXY_COUNT` > 0 (сколько обратных прокси стоит перед сервером), и берётся не
  первый элемент списка, а тот, что стоит перед дописанными прокси: заголовок пишет кто угодно.

## Конфигурация (env)

| Переменная      | Дефолт            | Смысл                                            |
|-----------------|-------------------|--------------------------------------------------|
| `LISTEN`        | `localhost:7171`  | адрес HTTP-сервера REST API                      |
| `API_JWT_SECRET`| — (**обязательна**) | секрет подписи JWT; без него сервер **не стартует**. Исключение: при `API_DEV_AUTH=true` пустой секрет заменяется случайным эфемерным (все токены протухают при рестарте) |
| `API_DEV_AUTH`  | `false`           | включает `POST /auth/dev` (только для разработки; при включении сервер пишет громкое предупреждение в лог)|
| `GEMINI_API_KEY`| `""`              | ключ Google Gemini для AI-распознавания расхода. Пустой → эндпоинт `/operations/parse` отдаёт `503`, остальной сервер работает как раньше |
| `GEMINI_MODEL`  | `gemini-3.1-flash-lite` | модель Gemini для распознавания |
| `AI_PARSE_RATE_PER_MIN` | `5`       | лимит запросов `/parse` на пользователя в минуту |
| `AI_PARSE_DAILY_QUOTA`  | `50`      | суточная квота запросов `/parse` на пользователя |
| `AI_MAX_BODY_BYTES`     | `15728640` (15 МБ) | общий лимит тела `/parse` (отдельно от глобального 1 МБ) |

Вход через внешних провайдеров (`cmd/splitty/config.go`). **Разделитель списков — `:`**, кроме
`ANDROID_CERT_SHA256` (см. ниже). Пустые элементы отфильтровываются (`nonEmptyValues` в `main.go`):
`envDefault:""` со сплитом даёт срез из одной пустой строки, а не пустой срез.

| Переменная | Дефолт | Смысл |
|---|---|---|
| `GOOGLE_CLIENT_IDS` | `""` | OAuth client id, чьи ID-токены принимаются (список допустимых `aud`), разделитель `:`. Пусто → `POST /auth/google` и `POST /me/link/google` отдают `503`. **Android-клиенты сюда не кладутся**: Credential Manager выпускает токен с `aud` = серверного (Web) client id |
| `APPLE_CLIENT_IDS` | `""` | client id Sign in with Apple: bundle id приложения и/или Services ID, разделитель `:`. Пусто → `POST /auth/apple` и `POST /me/link/apple` отдают `503`, **а также выключается обмен и отзыв токенов** (`initAppleTokens` вернёт `nil` даже при заданном `.p8`). ⚠️ **Порядок значим: bundle id обязан быть первым** — `clientIDs[0]` подставляется в `client_secret` token-эндпоинтов Apple |
| `APPLE_TEAM_ID` | `""` | Team ID для подписи client_secret token-эндпоинтов Apple |
| `APPLE_KEY_ID` | `""` | Key ID ключа Sign in with Apple (`.p8`) |
| `APPLE_PRIVATE_KEY` | `""` | **СОДЕРЖИМОЕ** файла `.p8` (не путь!). Нужен для обмена `authorizationCode` и отзыва токенов через `POST https://appleid.apple.com/auth/revoke` при удалении аккаунта (Apple Guideline 5.1.1(v)). Пусто → обмен и отзыв выключены, вход через Apple при этом работает. **В git не коммитится никогда** |
| `PUBLIC_BASE_URL` | `""` | https-адрес сервера; он же выключатель диплинка: пусто → `/join/{roomId}` и оба `.well-known` отдают `404`, а `inviteUrl` в `GET /rooms/{id}` не отдаётся. ⚠️ Одной этой переменной **недостаточно**: тот же домен прописывается в `android:host` (AndroidManifest.xml) и в `applinks:` (`ios/project.yml` **и** `ios/Splitty/Splitty.entitlements`), после чего оба клиента пересобираются |
| `IOS_APP_ID` | `""` | `<TeamID>.<bundle id>` (например `K8922Y6R3M.com.zagir.splitty`) для `apple-app-site-association`. Пусто → этот файл `404` |
| `ANDROID_PACKAGE` | `""` | имя пакета (`com.zagir.splitty`) для `assetlinks.json`; из него же собирается ссылка на Google Play на странице `/join` |
| `ANDROID_CERT_SHA256` | `""` | SHA-256 отпечатки подписи для `assetlinks.json`. **Разделитель здесь `,`, а не `:`** — сам отпечаток состоит из байтов через двоеточие (`E6:8C:8C:…`). Отпечатков может быть несколько (Play App Signing + локальный debug-ключ). Пусто → `assetlinks.json` `404` |
| `IOS_STORE_URL` | `""` | ссылка на карточку в App Store для страницы `/join`; пусто → кнопка не рисуется |
| `TRUSTED_PROXY_COUNT` | `0` | сколько обратных прокси стоит перед сервером. `0` — прямые соединения: `X-Forwarded-For` не читается вовсе, лимиты считаются по `RemoteAddr` |

Схема кнопки «Открыть в приложении» — константа `splitty://join/<roomId>`, а не настройка: она
вшита в `ios/project.yml` и `AndroidManifest.xml`, деплой её изменить не может.

⚠️ **Переменная, добавленная только в `.env`, до контейнера не доедет.** `docker-compose.yml`
пробрасывает внутрь лишь то, что перечислено поимённо в `services.telegram-bot.environment` —
новая настройка добавляется и в `.env.example`, и туда.

⚠️ **Семантика `REVIEW_USER_ID` и `DAILY_EXPENSES_USERS` изменилась**: оба означают теперь
**номера Splitty** (`_id`), а не telegram id — обе настройки ходят в `UserService.FindById`.
У существующих пользователей значения совпадают, новые записи вносить нужно по `_id`.
Подробнее — «Модель личности» в [README](../README.md).

Бот становится **опциональным**: если Telegram API не инициализировался (пустой/битый `TG_TOKEN`),
приложение пишет warning и продолжает работать только с REST API. REST-сервер и бот работают параллельно
(бот — `app.Do(ctx)`, сервер — в отдельной горутине, graceful shutdown через `closer`).

## DTO

```jsonc
// User
// deleted — аккаунт удалён; поле приходит ТОЛЬКО в /friends и только когда true
//   (снимок удалённого в комнате не исчезает, а анонимизируется, поэтому такой
//   человек продолжает попадать в список друзей; звать его в группу бессмысленно —
//   POST /rooms/{id}/members вернёт 404). Клиенты прячут такие строки из выбора
//   при приглашении
{"id": 123, "username": "zagir", "displayName": "Загир", "deleted": true}

// Me (профиль текущего пользователя)
// id — номер Splitty (не telegram id, см. «Общие правила»)
// linkedProviders — привязанные способы входа в стабильном порядке
//   ("telegram", "google", "apple", "password"); всегда массив, не null. Наружу
//   отдаётся ТОЛЬКО факт привязки: сами sub и telegram id остаются в базе.
//   "password" появляется, только когда войти паролем реально можно (есть и
//   адрес входа, и хеш)
// loginEmail — адрес входа по паролю; поля нет, если адреса у аккаунта нет.
//   Остаётся и после отвязки пароля: по нему клиент показывает, что пароль
//   можно задать заново. Уходит только ВЛАДЕЛЬЦУ (/me, /auth/*, /me/link/*)
{"id": 123, "username": "zagir", "displayName": "Загир", "lang": "ru",
 "linkedProviders": ["telegram", "google"], "notificationOn": true,
 "loginEmail": "user@example.com"}

// Debt — debtor должен lender'у sum
{"debtor": User, "lender": User, "sum": 500}

// OperationRecipient — доля получателя в целых рублях:
// для equally — каноническая вычисленная, для by_exact_amount — хранимая
{"user": User, "sum": 400}

// Operation
{
  "id": "65a...f", "description": "Ужин", "sum": 1200,
  "isDebtRepayment": false,
  "splitType": "equally",    // "equally" | "by_exact_amount"; у погашений отсутствует
  "donor": User,             // кто заплатил
  "recipients": [OperationRecipient],  // доли получателей, Σ sum долей == sum операции
  "createdAt": "2026-07-05T12:00:00Z",
  "files": [{"type": "image", "fileId": "AgAC..."}],  // может быть пустым/отсутствовать
  "items": [OperationItem],  // детализация по позициям чека — ТОЛЬКО у itemized-операций
                             // (AI-распознанных); отсутствует/nil у обычных. Плоские
                             // recipients выше — источник долгов, items — «зачем так вышло»
  "clientOpId": "3b2f1c9e-…"  // клиентский идемпотентный ключ (см. «Идемпотентность создания»);
                              // присутствует только если операция создана через REST с ним
}

// OperationItem — позиция чека в ответе (read-path). Отдаётся в Operation.items.
{
  "name": "Пицца",
  "price": 1200,          // ВСЕГДА суммарная стоимость строки (не цена единицы)
  "qty": 2,               // только для отображения («×2»); в делёж НЕ входит
  "shares": [ItemShare],  // доли участников по позиции (у сборов пусто, omitempty)
  "kind": "item",         // "item" | "surcharge" (сервисный сбор/доставка)
  "split": "proportional",// только у surcharge: "proportional" | "equally"; иначе отсутствует
  "percent": 10           // только для показа («Сбор 10%»); в расчёте НЕ участвует (omitempty)
}

// ItemShare — доля участника в позиции
{
  "userId": 123,
  "weight": 1,    // относительный вес доли; 1 = поровну
  "amount": 500   // фикс-сумма участника (omitempty); задана → weight игнорируется
}

// Currency (запись справочника валют)
{"code": "RUB", "symbol": "₽", "flag": "🇷🇺"}

// RoomSummary (строка списка групп)
{
  "id": "65a...f", "name": "Сплит по Стамбулу", "createdAt": "...",
  "isArchived": false,
  "currency": "RUB",     // валюта комнаты; пустая в базе → "RUB"
  "members": [User], "memberCount": 4,
  "totalSpent": 34000,   // сумма всех расходов комнаты (без погашений)
  "myBalance": 500,      // >0 — мне должны, <0 — я должен, 0 — расчёт
  "debtsUnavailable": true, // только у «неисчислимых» комнат (omitempty): долги
                            // не считаются на легаси-данных, myBalance отдан нулём
  "unreadCount": 3       // непрочитанные события ЭТОЙ группы (omitempty); 100 = «больше 99»
}

// RoomDetail (экран группы одним запросом)
{
  "id": "...", "name": "...", "createdAt": "...", "isArchived": false,
  "currency": "RUB",
  "members": [User],
  "totalSpent": 34000, "mySpent": 8500,   // mySpent — моя доля расходов
  "myBalance": 500,
  "debts": [Debt],                        // все долги комнаты
  "debtsUnavailable": true,               // только у «неисчислимых» комнат (omitempty):
                                          // debts=[] и myBalance=0, остальное — как обычно
  "operations": [Operation],              // все операции, новые первыми
  "seenThrough": "…"                      // время формирования ЭТОГО ответа: его клиент
                                          // возвращает в POST /rooms/{id}/notifications-seen
}

// FriendBalance (вкладка «Друзья»)
{
  "user": User,
  // итог по каждой валюте отдельно (валюты не складываются), только ненулевые;
  // порядок — как в справочнике валют. >0 — друг должен мне, <0 — я должен другу
  "totalsByCurrency": [{"currency": "RUB", "sum": 500}, {"currency": "USD", "sum": -100}],
  "rooms": [{"roomId": "...", "roomName": "...", "currency": "RUB", "balance": 500}]  // только ненулевые
}

// ActivityItem
{"roomId": "...", "roomName": "...", "roomCurrency": "RUB", "operation": Operation}

// InviteCard (закреплённая карточка раздела «Уведомления»)
// status — "added" (человека добавили) или "pending" (ждёт его решения)
// createdAt — время ПОСЛЕДНЕЙ смены отношения, а не первого приглашения
// roomName/inviterName приходят пустыми строками, если комнату или
//   пригласившего успели удалить: карточка не должна ронять весь ответ
{"roomId": "...", "roomName": "Поездка", "inviterName": "Загир",
 "status": "pending", "createdAt": "..."}

// Statistics (дашборд комнаты; только active-расходы, погашения исключены)
{
  "currency": "RUB",
  "totalSpent": 9400,          // сумма всех расходов комнаты
  "operationCount": 12,        // число всех расходов комнаты за всё время
  "monthSpent": 9400,          // расходы текущего календарного месяца (по create_at)
  "byDay": [{"date": "2026-07-05", "sum": 9400}],        // последние 30 дней, только дни с тратами, ISO-дата, по возрастанию
  "byMonth": [{"month": "2026-02", "sum": 0}, /* … */ {"month": "2026-07", "sum": 9400}],
  // ^ последние 6 календарных месяцев включая текущий, месяцы без трат — с sum=0, "yyyy-mm", по возрастанию
  "paidByMember": [{"user": User, "sum": 4500}],         // кто платил (донор), по убыванию суммы
  "shareByMember": [{"user": User, "sum": 3133}],        // чья доля потребления (получатели), по убыванию суммы
  "topOperations": [                                     // топ-5 расходов по сумме
    {"id": "...", "description": "Ужин", "sum": 3600, "donor": User, "createdAt": "..."}
  ]
}
```

`myBalance` считается из вычисленных долгов комнаты (`OperationService.GetAllDebts`):
`sum(долги где я lender) - sum(долги где я debtor)`.

## Эндпоинты

### Auth

`POST /api/v1/auth/telegram` — вход через Telegram Login Widget.
Тело: `{"id": 123, "firstName": "…", "lastName": "…", "username": "…", "photoUrl": "…", "authDate": 1720000000, "hash": "…"}`.
Проверка подписи: HMAC-SHA256 по data-check-string с ключом `SHA256(TG_TOKEN)` (стандарт Telegram);
`authDate` не старше **10 минут** (короткое окно против replay перехваченного payload). Upsert пользователя. Ответ: `{"token": "<jwt>", "user": Me}`.
`401 unauthorized` при неверном hash; `503` если `TG_TOKEN` не задан.

`POST /api/v1/auth/code` — вход по одноразовому коду из Telegram-бота.
Код выдаёт команда **`/login`** в личном чате бота: 8 символов из алфавита без неоднозначных
символов (`ABCDEFGHJKMNPQRSTUVWXYZ23456789`), TTL **5 минут**, одноразовый
(Mongo-коллекция `login_code`; проверка и пометка `used` атомарны — `FindOneAndUpdate`).
Тело: `{"code": "ABCD2345"}`, код регистронезависим. Ответ как выше: `{"token": "<jwt>", "user": Me}`.
`400 validation` если `code` не передан; `401 invalid_code` если код не найден, просрочен,
уже использован или пользователь не существует.

`POST /api/v1/auth/google` — вход по ID-токену Google.
Тело: `{"idToken": "<google id token>"}`. Токен проверяется по JWKS Google (подпись, издатель,
срок), `aud` обязан быть одним из `GOOGLE_CLIENT_IDS`. Пользователь ищется по `google_sub`;
не нашли — заводится новый с номером из аллокатора (telegram id у него нет).
Ответ: `{"token": "<jwt>", "user": Me}`.
`400 validation` если `idToken` пуст; `401 unauthorized` если токен не прошёл проверку (причина
наружу не раскрывается, детали — в логах); `429 rate_limited` при более чем 20 попытках с адреса
в минуту (бюджет отдельный от `/auth/code`); `503 unavailable` если `GOOGLE_CLIENT_IDS` не задан.

`POST /api/v1/auth/apple` — вход по ID-токену Sign in with Apple.
Тело: `{"idToken": "…", "nonce": "…", "displayName": "…", "authorizationCode": "…"}`.
- `nonce` — **обязателен** и присылается СЫРЫМ: в токене лежит его `SHA256` в hex, сервер сверяет
  их constant-time. Без него перехваченный или переигранный токен принимался бы как свежий вход;
- `displayName` — отдельным полем, потому что имени в ID-токене Apple нет: Apple отдаёт его
  клиенту один раз, при самом первом входе;
- `authorizationCode` — опционален и нужен не входу, а **удалению аккаунта**: сервер меняет его
  на refresh token, чтобы потом отозвать токены (`auth/revoke`, Guideline 5.1.1(v)). Обмен
  best-effort: пустой код, незаданный `APPLE_PRIVATE_KEY` или недоступный Apple логируются
  warning'ом, вход при этом проходит.

Пользователь ищется по `apple_sub`; не нашли — заводится новый с номером из аллокатора.
Ответ: `{"token": "<jwt>", "user": Me}`. Коды ошибок — как у `/auth/google`, плюс
`400 validation` при пустом `nonce` и `401 unauthorized` при несовпадении nonce.

**Аккаунты по email не склеиваются ни у Google, ни у Apple**, даже при полном совпадении почты:
почту меняют, а Apple по умолчанию выдаёт relay-адрес `xxx@privaterelay.appleid.com`,
принадлежащий паре «человек + приложение». Объединение способов входа — только явное,
через `POST /me/link/{provider}` из-под уже авторизованного токена.

`POST /api/v1/auth/register` — регистрация по email и паролю.
Тело: `{"email": "user@example.com", "password": "…", "displayName": "Загир"}`. Адрес хранится
в ОТДЕЛЬНОМ поле `login_email` (не в `email`, который заполняется best-effort из Google/Apple и
идентификатором не является), нормализованным: trim + нижний регистр, unique sparse индекс.
Пароль — bcrypt, минимум **8 символов**. Пользователь заводится с номером из аллокатора.
Ответ: `{"token": "<jwt>", "user": Me}`.
`400 validation` при невалидном email, коротком пароле или пустом `displayName`;
**`409 email_taken`** если адрес уже зарегистрирован; `429 rate_limited` (20 на адрес в минуту).

`POST /api/v1/auth/login` — вход по email и паролю. Тело: `{"email": "…", "password": "…"}`.
Ответ: `{"token": "<jwt>", "user": Me}`.
**`401 invalid_credentials`** — один и тот же ответ (статус, код и текст) и на неизвестный адрес,
и на неверный пароль: эндпоинт не должен быть оракулом «зарегистрирован ли такой email».

`POST /api/v1/me/password` — задать или сменить пароль (авторизованный).
Тело: `{"currentPassword"?: "…", "newPassword": "…"}` → `200` + `{"user": Me}`.
`currentPassword` обязателен, **только если пароль уже задан**.
`400 validation` при коротком пароле; **`403 invalid_password`** при неверном текущем
(намеренно не `401`, см. раздел «Ошибки»); `429 rate_limited` (20 в минуту на пользователя).

⚠️ **Инфраструктуры отправки писем нет**, поэтому нет ни подтверждения адреса, ни сброса пароля
по почте. Забытый пароль восстанавливается только так: войти другим привязанным способом
(Telegram/Google/Apple) → `DELETE /me/link/password` (адрес остаётся за аккаунтом) →
`POST /me/password` с новым паролем. **У аккаунта, где пароль был единственным способом входа,
восстановления нет по построению.** Аккаунты по email не склеиваются и здесь: регистрация с
адресом X и последующий вход через Google с тем же X дают два разных профиля.

`POST /api/v1/auth/dev` — вход для разработки (**только при `API_DEV_AUTH=true`**, иначе `404`).
Тело: `{"userId": 123, "displayName": "Загир", "username": "zagir"}` → upsert пользователя, ответ как выше.

### Профиль

- `GET /api/v1/me` → `Me`
- `PATCH /api/v1/me` — тело `{"displayName"?, "lang"?, "notificationOn"?}` → обновлённый `Me`.
- `DELETE /api/v1/me` → `204` — **удаление аккаунта** (обязательное требование Apple
  Guideline 5.1.1(v)). Порядок шагов фиксирован (`internal/rest/delete_account.go`):
  отзыв токенов Apple → tombstone (`deleted_at`, поля личности освобождаются под повторную
  регистрацию) → инвалидация кеша auth-middleware → анонимизация встроенных снимков во всех
  комнатах → чистка побочных коллекций с PII (`chat_state`, `bug_report`, `push_outbox`,
  `login_code`, `room_invite`). **Долги и суммы сохраняются**: id операций, значения и доли не меняются,
  имя удалённого заменяется плейсхолдером.
  Шаги после tombstone идемпотентны, поэтому упавший запрос доводится до конца повторным
  `DELETE /me` — единственный маршрут, который принимает токен уже удалённого аккаунта.
  `403 forbidden` на демо-аккаунте ревьюеров (`REVIEW_USER_ID`): иначе демо-вход умер бы
  до ручной правки базы. `401 unauthorized`, если документа пользователя уже нет.
  `500` со «повторите запрос», если чистка не завершилась.
  ⚠️ Инвалидация токена мгновенна **только для удаляющей сессии** (её запись в кеше
  auth-middleware чистится явно). Токены того же человека на ДРУГИХ устройствах продолжают
  работать до истечения `accountTTL` = 60 секунд.

### Способы входа (link/unlink)

- `POST /api/v1/me/link/{provider}` — привязка способа входа к **текущему** аккаунту
  (кто текущий — решает JWT, а не тело запроса). `provider`: `google` | `apple` | `telegram`
  (`password` здесь не поддерживается — см. `POST /me/password`).
  - `google`/`apple` — тело `{"idToken": "…", "nonce"?: "…", "authorizationCode"?: "…"}`;
    проверки те же, что при входе. Nonce сверяется, **когда он есть в токене** (значение
    подписано провайдером). `authorizationCode` — только Apple и **обязателен на практике**:
    код одноразовый, живёт минуты, и не обменяв его здесь, сервер навсегда лишается возможности
    отозвать токены Apple при удалении аккаунта (Guideline 5.1.1(v)). Обмен идёт после успешной
    привязки и является best-effort — недоступный Apple привязку не ломает;
  - `telegram` — тело и проверки те же, что у `POST /auth/telegram` (подпись виджета +
    `authDate` не старше 10 минут). Профиль (`username`/`displayName`) при этом намеренно
    не обновляется: у привязки ровно один эффект — личность.

  Ответ `200`: `{"user": Me, "warning"?: "…"}`. Идемпотентно: повторная привязка той же
  личности к тому же аккаунту — не ошибка.
  `400 validation` при пустом `idToken` (или при отсутствии `id`/`authDate`/`hash` у telegram);
  **`400 provider_rejected`** если ОТВЕРГНУТ ТОКЕН ПРОВАЙДЕРА (подпись, `aud`, срок, несовпавший
  nonce) — статус намеренно не `401`, см. раздел «Ошибки»;
  `404 not_found` при неизвестном провайдере; `503 unavailable` если провайдер не сконфигурирован;
  `429 rate_limited` при более чем 20 попытках в минуту на пользователя;
  `401 unauthorized` при неверной подписи telegram, протухшем `authDate` или если аккаунт удалён
  параллельным `DELETE /me`;
  **`409 identity_taken`** если эта личность уже принадлежит другому профилю Splitty;
  **`409 identity_already_linked`** если у текущего аккаунта этот провайдер уже занят ДРУГОЙ
  личностью — второй аккаунт того же провайдера не привязывается, сначала нужно отвязать
  текущий. Молчаливая замена запрещена: для Apple она отцепила бы прежний `apple_sub` без
  `auth/revoke` (Guideline 5.1.1(v)) и затёрла бы его `apple_refresh_token`, для Google —
  тихо отобрала бы у человека первый способ входа вместо обещанного второго.
- `DELETE /api/v1/me/link/{provider}` → `200` + `{"user": Me, "warning"?: "…"}` — отвязка.
  Идемпотентна (отвязывать нечего — тот же `200`). **`409 last_identity`**, если это последний
  способ входа: аккаунт остался бы недоступен навсегда после протухания 90-дневного токена.
  Отвязка `apple` дополнительно **отзывает токены Apple** (строго до чистки) и убирает
  `apple_refresh_token` из документа: держать рабочий секрет от личности, которой у пользователя
  больше нет, незачем.
  Отвязка `password` убирает ХЕШ, но оставляет `login_email` за аккаунтом: иначе «задать новый
  пароль из профиля» вернуло бы пароль без адреса, то есть неработающий вход. Привязки
  (`POST /me/link/password`) нет — пароль задаётся через `POST /me/password`.
  Отвязка `telegram` дополнительно возвращает `warning` и чистит `chat_state`: у исторического
  пользователя `_id == telegram id`, поэтому следующий `/start` в боте заведёт ему ОТДЕЛЬНЫЙ
  новый профиль без групп, и привязать этот telegram обратно уже не выйдет (`409 identity_taken`).

⚠️ **Слияние двух существующих аккаунтов не поддерживается** — это и есть `409 identity_taken`.
Причина — денормализация: снимки пользователя (`id`, `display_name`, `user_name`) встроены в
документы комнат и операций, и «перенести данные» означает переписать их во всех комнатах обоих
профилей. Подробнее — «Модель личности» в [README](../README.md).

### Комнаты (группы)

- `GET /api/v1/rooms?archived=false` → `[RoomSummary]` (сортировка: новые первыми). `archived=true` — архив.
  `unreadCount` — непрочитанные события **этой** группы: бейдж на вкладке говорит, ЧТО
  что-то случилось, счётчик на карточке — ГДЕ. «Непрочитанное» здесь значит ровно то же,
  что и для бейджа раздела «Уведомления» (адресовано лично тебе — по `notification_sent`
  операции, с откатом на правило по долям; см. ниже), но новее отметки **по этой комнате**.
  Отметка — `users.rooms_seen_at.<roomId>`; её ставит только открытие самой группы
  (`POST /rooms/{roomId}/notifications-seen`).
  **Отметки по комнате нет** — читается общая `users.notifications_seen_at`. Фоллбэк
  обязателен, а не «приятная мелочь»: своей отметки в день выкатки нет ни у кого, и без
  него загорелись бы разом ВСЕ карточки у всех — та же ловушка «99+ каждому», ради
  которой делали бэкфилл `repository.BackfillNotificationsSeenAt`. Он же проставил общей
  отметке момент выкатки, поэтому раскатка проходит молча и без новой миграции.
  Из этого следует и граница: группу, которую человек ещё ни разу не открывал ПОСЛЕ
  выкатки, заход в раздел «Уведомления» гасит — раздел показывает те же события. Как
  только группу открыли хоть раз, у неё появляется своя отметка, и раздел на её счётчик
  больше не влияет.
  Значение точное до **99**; **100** означает «больше 99» — клиент рисует «99+»
  (тот же потолок, что у бейджа раздела). Считается по уже загруженным документам комнат:
  дополнительных запросов на комнату этот счётчик не делает.
  Приглашения в счётчик карточки не входят: непринятое приглашение — это ещё не группа,
  его место в разделе «Уведомления» (и в его бейдже).
- `POST /api/v1/rooms` — `{"name": "…"}` → `201` + `RoomDetail`. Создатель — первый участник. Имя: непустое, ≤ 100 символов.
- `GET /api/v1/rooms/{roomId}` → `RoomDetail`. `403` если пользователь не участник, `404` если нет комнаты.
  Поле `inviteUrl` (`<PUBLIC_BASE_URL>/join/<roomId>`) отдаётся, только когда домен настроен;
  иначе поле отсутствует и клиент показывает ссылку через бота.
- `POST /api/v1/rooms/{roomId}/notifications-seen` — отметить прочитанной ЭТУ группу
  (гасит `unreadCount` её карточки в списке). Тело и проверки те же, что у глобальной
  `POST /me/notifications-seen`: `{"seenThrough": "…"}` → `204`; значение берётся **из
  ответа** `GET /rooms/{roomId}` (поле `seenThrough` — серверное время формирования того
  ответа, снятое до чтения комнаты), отметка двигается только вперёд, `400 validation` на
  пустое время и на время из будущего дальше чем на минуту. `403`/`404` — как на любом
  маршруте комнаты (не участник / комнаты нет).
  Отметка отдельная от глобальной намеренно: раздел «Уведомления» не должен гасить
  счётчики групп — в раздел человека ведёт как раз бейдж, и счётчики почти никто не
  успевал бы увидеть. Хранится как `users.rooms_seen_at.<roomId>` — картой на документе
  пользователя, чтобы удаление аккаунта уносило отметки само (отдельную коллекцию
  пришлось бы дописывать в чистку руками).
- `POST /api/v1/rooms/{roomId}/join` → `RoomDetail`. Идемпотентно (повторный join — ок). Это и есть «присоединение по приглашению»: код приглашения = `roomId` (совместимо с deep-link бота `t.me/<bot>?start=room<roomId>`).
- `POST /api/v1/rooms/{roomId}/archive` → `204` (только для участника; помечает архивной только для него — `room_states.archived`).
- `POST /api/v1/rooms/{roomId}/unarchive` → `204`.
- `PUT /api/v1/rooms/{roomId}/currency` — смена валюты комнаты (общая для всех участников,
  тот же `RoomRepository.UpdateCurrency`, что у бота). Тело: `{"currency": "USD"}` → `204`.
  `400 validation` если код не из справочника; `403` если пользователь не участник; `404` если комнаты нет.

### Состав группы (позвать, выйти, убрать)

Основной путь в группу — **приглашение от участника**, а не код: у друга уже есть id,
запоминать и вводить нечего. Код (`POST /rooms/{roomId}/join` выше) остаётся точкой
приземления диплинка и запасным путём для посторонних, которым прислали ссылку.

- `POST /api/v1/rooms/{roomId}/members` — позвать. Тело: `{"userId": 42}` →
  `200 {"status": "added"}`, если человек уже в комнате, или `202 {"status": "pending"}`,
  если приглашение ждёт его решения.
  Звать без согласия можно только друга — со-участника хотя бы одной общей неархивной
  комнаты; иначе `403 not_a_friend`. Если по этой комнате запись отношения (`room_invite`)
  уже есть, проверка дружбы не нужна вовсе: такой человек в любом случае получит
  `pending` и решит сам. Ветка обязательна — вышедший перестаёт быть другом, если общая
  комната была единственной, и «только друзья» сделали бы повторное приглашение
  недостижимым.
  Идемпотентно во всех состояниях: повторный вызов не дублирует участника и **не шлёт
  второй push** — ни когда человек уже добавлен, ни когда приглашение уже `pending`.
  `added` — человек добавлен сразу и уже в комнате; `pending` — запись отношения по этой
  комнате есть, а участником он сейчас не является: молча вернуть его нельзя, он попадёт
  в комнату только после явного согласия (accept ниже).
  Решает именно **членство**, а не хранимый в записи статус. Членство и запись лежат в
  разных документах, транзакций между ними нет (mongo развёрнут одним узлом), поэтому
  `added` у не-участника — штатный исход гонки «добавили × вышел», а не битые данные.
  Прежняя ветка по статусу (`left`/`declined`) такого человека пропускала бы в прямое
  добавление, то есть возвращала бы его в группу без спроса. `403` если сам вызывающий не участник, `404` если
  приглашаемого нет (или он удалён), `400 validation` на пустой/нулевой `userId`, на
  приглашение самого себя и на кривое тело, `503 unavailable` если хранилище приглашений
  не подключено.
- `DELETE /api/v1/rooms/{roomId}/members/me` — выйти из группы → `204`.
  `409 has_operations`, если на человеке висит хоть одна активная операция (он донор
  или получатель, независимо от размера доли) — выход бы порвал расчёты остальных. Выход
  открывается сам, как только человек убран из расходов, **править их вправе любой
  участник**.
  `409 last_member` — последний участник выйти не может: комната осталась бы сиротой.
  `403` если он не участник, `404` если комнаты нет.
  Проверка расходов повторена **условием в самой записи выхода**: расход, заведённый на
  человека уже после проверки, отменяет выход тем же `409 has_operations` — иначе долг
  оставался бы на том, кто комнату больше не видит.
- `DELETE /api/v1/rooms/{roomId}/members/{userId}` — убрать участника → `204`.
  Доступно любому участнику: это лекарство от «позвал не того», а в комнате все равны
  (расходы тоже правит кто угодно). Условия те же (`409 has_operations`).
  Себя этим маршрутом убрать нельзя — `400 validation` с указанием на `…/members/me`:
  два пути к одному действию с разными текстами ошибок путали бы и клиент, и человека.
  `403` если вызывающий не участник, `404` если удаляемого в комнате нет, если комнаты
  нет и если `{userId}` не число.
- `POST /api/v1/invites/{roomId}/accept` → `200 {"status": "added"}` — принять
  `pending`-приглашение (человек становится участником). `404`, если комнату успели
  удалить (статус приглашения при этом остаётся `pending`). Если вход в комнату не
  удался (`500`), статус **возвращается в `pending`**: иначе повтор упирался бы в
  `409 not_pending`, и починить приглашение сам человек не мог бы.
- `POST /api/v1/invites/{roomId}/decline` → `200 {"status": "declined"}` — отклонить:
  участником он не станет, повторно позвать его можно. Отказ от приглашения в удалённую
  комнату — тоже `200`.
  Отказ **участника** — `409 not_pending`: членство у него уже есть, «Отклонить» из
  группы не выводит (для этого `DELETE …/members/me`), а `declined` на участнике
  противоречил бы его же членству. Состояние «участник + `pending`» возникает штатно —
  откат неудавшегося accept и примирение после входа по ссылке решают по снимку комнаты,
  а тот стареет; в разделе «Уведомления» такая карточка показывается как `added`.
  Оба: `404`, если `pending`-приглашения на этого человека нет; `409 not_pending`, если
  оно уже принято или отклонено — конкурентные accept и decline дают ровно один успех;
  `503 unavailable` если хранилище приглашений не подключено.
- Вход по коду/ссылке (`POST /rooms/{roomId}/join`) **примиряет** запись приглашения:
  прошедший по ссылке `pending`-приглашённый переводится в `added`, иначе раздел
  «Уведомления» вечно предлагал бы ему решение по комнате, где он уже состоит.

### Валюты

- `GET /api/v1/currencies` → `[Currency]` — справочник поддерживаемых валют для пикера
  в приложении, стабильный порядок: `RUB`, `USD`, `EUR`, `IDR`, `KZT`, `UZS`.

### Операции (расходы)

- `GET /api/v1/rooms/{roomId}/operations?type=all|spend|repayment` (дефолт `all`) → `[Operation]`, новые первыми.
- `POST /api/v1/rooms/{roomId}/operations` → `201` + `Operation`.
  Тело — **ровно один** из двух режимов деления (`400`, если заданы оба или ни одного):
  - поровну (`splitType: equally`):
    `{"description": "Ужин", "sum": 1200, "donorId": 123, "recipientIds": [123, 456]}` —
    сервер раскладывает доли по каноническому правилу (см. «Общие правила»): `base = S/n`,
    остаток `S % n` по рублю первым получателям **в порядке массива** `recipientIds`
    (дубликаты id схлопываются);
  - точными суммами (`splitType: by_exact_amount`):
    `{"description": "Отель", "sum": 1200, "donorId": 123, "recipientSums": [{"userId": 123, "sum": 700}, {"userId": 456, "sum": 500}]}` —
    суммы целые, `>= 1`, каждый получатель не более одного раза, `Σ sum == sum` операции (`400` при расхождении).

  Общие правила: участник комнаты может добавлять; `donorId` и все получатели — участники комнаты;
  `sum >= 1`; `description` непустое. Членство проверяется **дважды**: по прочитанной
  комнате (`400 validation`) и условием в самой вставке — если участника успели убрать,
  пока запрос шёл, расход не записывается и приходит `409 conflict` («состав группы
  изменился»). Долг на не-участнике был бы невыводим: комнату он больше не видит. Операция сохраняется в модели develop:
  `status=active` (у REST нет драфт-шага бота), `splitType`, `recipients_with_sum`;
  `IsDebtRepayment=false`, `CreateAt=now`, новый `ObjectID`.
  Тело может содержать опциональный `clientOpId` — см. «Идемпотентность создания»
  (повтор с тем же ключом → `200` + существующая операция вместо `201`).

  **Itemized-режим (позиции чека, `items`).** Тело может нести **опциональный** массив
  `items: [OperationItem]` (детализация из AI-распознавания, см. `POST /operations/parse`).
  Когда `items` присутствует и непуст, он становится **источником правды**:
  - сервер **сам выводит** `recipients` (доли) и `sum` из позиций (`api.DeriveShares`) и
    **игнорирует** плоские клиентские поля `sum`/`recipientIds`/`recipientSums`;
  - `splitType` результата — всегда `by_exact_amount`;
  - позиции сохраняются в операцию (`Operation.items`) и отдаются на read-path;
  - валидация: `description` непустое; `donorId` — участник комнаты; все `userId` из
    `items[].shares` — участники комнаты (иначе `400`); поле `unknown` каждой позиции
    **должно быть пустым** — при непустом `400 validation` («сначала выберите, кто такие …»);
    позиции должны раскладываться без ошибки (перебор фиксов над ценой → `400`).

  Формат `OperationItem`/`ItemShare` — см. раздел «DTO». Клиент присылает позиции в том же
  виде, что вернул `/parse` (поле `unknown` к моменту сохранения — пустое).
- `PUT /api/v1/rooms/{roomId}/operations/{operationId}` — то же тело → `Operation`.
  **Право: любой участник комнаты** (посторонним — `403`; Splitwise-семантика, автор изменения виден в Telegram-уведомлении). Погашения (`isDebtRepayment=true`) редактировать нельзя (`409 conflict`).
  `items` работает так же, как в `POST` (сервер выводит суммы). **Плоское обновление
  без `items` затирает сохранённые позиции** (`Operation.items` → `nil`): старые клиенты
  (бот, Android, старые версии iOS) редактируют itemized-операцию плоско и не разъезжаются
  с сервером — детализация просто сбрасывается, плоские суммы остаются валидными.
- `DELETE /api/v1/rooms/{roomId}/operations/{operationId}` → `204`. Право: любой участник комнаты. Погашение удалять можно (отмена платежа).

### AI-распознавание расхода (parse)

- `POST /api/v1/rooms/{roomId}/operations/parse` — распознаёт расход из **голоса**,
  **фото чека** или **текста** в структурированный черновик. **Ничего не создаёт и не хранит** —
  это чистая функция «черновик + ввод → черновик» (**stateless**): один и тот же вызов
  используется и для распознавания с нуля, и для голосовой правки (тогда передаётся
  текущий `draft`). Сохранение — обычным `POST/PUT /operations` с полем `items`.

  Тело — **`multipart/form-data`**; части `audio`, `image` и `text` можно передавать в
  **любой комбинации** (нужна хотя бы одна). Если пришли и фото, и голос, модель берёт
  позиции и цены с фото, а распределение по людям — из надиктовки:
  - `audio` — файловая часть, `Content-Type` из allowlist: `audio/wav` (основной для iOS —
    PCM16 16 кГц моно), `audio/x-wav`, `audio/aac`, `audio/mpeg`, `audio/mp3`,
    `audio/ogg`, `audio/flac`;
  - `image` — файловая часть, `Content-Type`: `image/jpeg` (основной), `image/png`,
    `image/webp`, `image/heic`;
  - `text` — обычное поле формы (строка);
  - `draft` — **опциональное** поле формы: JSON текущего черновика (`Draft`) для голосовой
    правки. При его наличии модель применяет дельту, не пересобирая уже проставленные доли.

  Ответ `200`:
  ```jsonc
  {
    "draft": Draft,          // обновлённый черновик (см. ниже)
    "questions": ["кто платил?", "не расслышал сумму"]  // уточняющие вопросы, omitempty
  }
  ```

  Форма черновика (транспортный контракт, тот же тип используется в `items` при сохранении):
  ```jsonc
  // Draft
  {
    "description": "Ужин",
    "sum": 4700,
    "donorId": 123,          // кто платил (omitempty; null если модель не поняла)
    "items": [DraftItem]     // позиции чека (omitempty)
  }

  // DraftItem — как OperationItem (см. «DTO»), плюс поле unknown:
  {
    "name": "Пицца", "price": 1200, "qty": 2,   // price=0 — «цена не распознана»:
                             // позиция остаётся в черновике, модель задаёт уточняющий
                             // вопрос, сохранение блокируется до заполнения цены
    "shares": [{"userId": 123, "weight": 1, "amount": 500}],  // amount — фикс-сумма (omitempty)
    "kind": "item",          // "item" | "surcharge"
    "split": "proportional", // только surcharge: "proportional" | "equally"
    "percent": 10,           // только display (omitempty), в расчёте не участвует
    "unknown": ["саня"]      // имена, которые модель не сматчила участникам (omitempty);
                             // пользователь разрешает их в UI. Пока unknown непуст —
                             // операцию с этими items сохранить нельзя (400 на записи)
  }
  ```

  Семантика полей позиции — как у `OperationItem` (раздел «DTO»): `price` — всегда total
  строки; `qty` — только display; у `surcharge` сумма берётся из `price` (`percent` — только
  показ), доли считаются от базовых долей людей по правилу `split`.

  `sum` черновика выводится из `items`, когда они непусты; у плоского черновика (без
  позиций) остаётся оценка модели. Черновик, состоящий ТОЛЬКО из надбавок (`surcharge`),
  возвращается плоским: позиции отбрасываются, сумма сохраняется.

  **Доступ и защиты:**
  - auth обязателен (`401` без токена); пользователь — участник комнаты (`403` иначе);
  - «я/меня/мне» в надиктовке модель относит к **автору запроса** (userId из токена) —
    клиенту передавать ничего не нужно;
  - **rate-limit** на пользователя (запросов/мин + суточная квота): при превышении
    `429 rate_limited` (проверяется **до** чтения больших частей и вызова модели);
  - `503 ai_disabled` если AI выключен (не задан `GEMINI_API_KEY`);
  - лимиты тела: общий `AI_MAX_BODY_BYTES` (~15 МБ, **отдельно** от глобального 1 МБ —
    для этого пути глобальный лимит снят), покусочно `audio ≤ 3 МБ`, `image ≤ 8 МБ`,
    `draft ≤ 64 КБ`; превышение — `413 too_large`;
  - неподдерживаемый `Content-Type` части — `415 unsupported_media`;
  - `400 validation` если не передан ни один вид ввода или `draft` невалиден;
  - при ошибке модели — `502` с телом `{draft, questions}`, где `draft` — **эхо входного
    черновика** (то, что пользователь уже надиктовал, не теряется).

### Прозвища участников (aliases)

- `POST /api/v1/users/{userId}/aliases` — добавляет пользователю прозвище, чтобы AI сматчил
  его в следующий раз (нераспознанное имя из `unknown` → выбор человека → дозапись алиаса).
  Тело: `{"alias": "Саня"}` → `204 No Content`. Алиас нормализуется (`trim` + нижний регистр),
  хранится с дедупликацией (`$addToSet`).
  Право: в **свой** профиль — всегда; в чужой — только если есть **общая комната**
  с `userId` (`403 forbidden` иначе). Пустой алиас — `400 validation`.

### Долги и погашение (settle up)

- `GET /api/v1/rooms/{roomId}/debts?involving=all|me` (дефолт `all`) → `[Debt]`.
  Долги считаются расчётом develop (`service.GetRoomDebts`) по активным операциям
  (легаси-операции — с синтезированными долями, см. «Общие правила»).
  «Неисчислимая» комната (см. «Общие правила») отдаёт `200` и пустой список.
- `POST /api/v1/rooms/{roomId}/repayments` → `201` + `Operation`.
  Тело: `{"debtorId": 123, "lenderId": 456, "sum": 500}`.
  Создаёт операцию как бот develop: `IsDebtRepayment: true`, `status: active`, `Donor: debtor`,
  `recipients_with_sum: [{lender, sum}]`, без `splitType`.
  Правила: текущий пользователь — один из `debtorId`/`lenderId`; оба — участники; `sum >= 1`;
  `sum <=` текущего долга debtor→lender (`409 conflict` если больше или долга нет).
  В «неисчислимой» комнате (см. «Общие правила») долги не считаются, гасить нечего —
  `409 conflict` с сообщением «долги этой группы не считаются из-за старых данных», не `500`.
  Конкурентные погашения одного долга (mongo без транзакций) разрешаются компенсацией:
  если после вставки долг ушёл в минус, погашение откатывается и возвращается `409 conflict` —
  клиент перечитывает долги и при необходимости повторяет запрос.
  Тело может содержать опциональный `clientOpId` — см. «Идемпотентность создания»:
  повтор с тем же ключом возвращает `200` + существующее погашение **до** проверки долга
  (первая доставка долг уже погасила, иначе повтор получал бы ложный `409`).

### Идемпотентность создания (clientOpId)

Офлайн-клиенты (iOS/Android) копят операции в локальном **outbox** и досылают их при появлении
сети. Доставка «хотя бы один раз»: ответ сервера мог потеряться после успешной вставки, и повтор
того же запроса без защиты создал бы дубль расхода/погашения. Поэтому:

- `POST /rooms/{roomId}/operations` и `POST /rooms/{roomId}/repayments` принимают
  **опциональное** поле `clientOpId` — клиентский идемпотентный ключ (UUID, который клиент
  генерирует при постановке операции в outbox). Формат: ≤ 64 символов из `[A-Za-z0-9-]`,
  иначе `400 validation`. Без поля поведение прежнее (каждый POST создаёт операцию).
- Семантика: если в комнате **уже есть** операция с таким `client_op_id`, дубль не создаётся —
  возвращается **`200`** + существующая `Operation`. Первая успешная вставка отвечает **`201`**.
  Клиент трактует оба кода как успех и сопоставляет локальную запись с серверной по `clientOpId`
  (он отдаётся в `Operation`).
- Ключ уникален **в пределах комнаты** и хранится в операции (`bson client_op_id`, пустой не
  сериализуется; операции бота ключа не имеют). Тело повтора не сравнивается с существующей
  операцией — ответственность за «один ключ = одна операция» на клиенте.
- Гонки: проверка и вставка выполняются **атомарно** — одним `UpdateOne` с фильтром
  `{_id, "operations.client_op_id": {$ne: clientOpId}}` и `$push`; конкурентные повторы одного
  ключа дают ровно одну операцию (`201` победителю, `200` остальным).
- В `PUT /operations/{operationId}` поле игнорируется: хранимый ключ операции не меняется.

### Telegram-уведомления о мутациях

Успешные мутации через REST шлют участникам комнаты **те же telegram-уведомления, что и бот**
(`bot.Notifier`, тексты — ключи `scrn_notification_*`/`scrn_debt_returned_recepient` из
`conf/lang/*.ini`, язык — настройка получателя, суммы — в валюте комнаты, с inline-кнопками
«Посмотреть операцию»/«В тусу»). Набор событий — строгий паритет со сценариями бота
(`internal/bot/operation_screen.go`), ничего сверх бота не выдумано:

- `POST /operations` (создание): назначенному плательщику, если он не автор запроса —
  «назначил(а) тебя плательщиком»; каждому получателю с ненулевой долей (кроме автора) —
  «добавил(а) тебя в операцию» с его долей. Уведомлённые помечаются в `notification_sent`
  операции (как у бота). Идемпотентный **повтор** с тем же `clientOpId` не уведомляет второй раз.
- `PUT /operations/{id}` (изменение): по диффу old/new, как в боте — смена плательщика
  (обоим донорам, кроме автора), изменение названия/добавление фото (всем участникам операции),
  добавленным получателям, получателям с изменённой долей, удалённым получателям.
- `DELETE /operations/{id}` (удаление расхода): каждому получателю — «убрал(а) тебя из операции»
  (у бота удаление реализовано как «изменение, убравшее всех получателей»). Удаление
  **погашения** не уведомляет — у бота нет такого сценария/текста.
- `POST /repayments` (погашение): кредитору — «тебе был возвращён долг», если погашение создал
  должник. Если погашение подтвердил сам кредитор — никто не уведомляется (текста для должника
  у бота нет). Откатившееся компенсацией погашение (`409`) не уведомляет.

Общие правила: автор мутации никогда не уведомляется; `notificationOn` получателя уважается
(`nil` → включено; исключения — паритет с ботом: смена плательщика и возврат долга уходят без
этой проверки, как в боте). Отправка — **после успешной записи, в фоне** (ответ клиенту не ждёт
telegram), ошибки отправки только логируются. Уведомления работают только когда бот
сконфигурирован (`TG_TOKEN` задан); без бота REST работает как раньше, уведомления — no-op.

### Друзья и активность (агрегаты по всем неархивным комнатам пользователя)

- `GET /api/v1/friends` → `[FriendBalance]` — все со-участники по всем моим неархивным комнатам;
  `totalsByCurrency` — нетто по вычисленным долгам всех комнат **с разбивкой по валютам**
  (валюты не складываются; только ненулевые итоги, порядок — как в справочнике валют).
  Сортировка: сначала ненулевые (по сумме модулей итогов всех валют, убыв.), потом рассчитанные.
  Вклад «неисчислимых» комнат (см. «Общие правила») пропускается и не рушит агрегат;
  друзья из таких комнат остаются в списке (с нулевым вкладом от этих комнат).
- `GET /api/v1/activity?limit=30&offset=0` → `[ActivityItem]` — операции всех моих неархивных комнат, новые первыми.
  `limit` ограничен диапазоном 1..100 (значения сверх — клампятся), `offset >= 0`; `offset` за концом списка — пустой ответ.
  Оставлен для обратной совместимости со старыми клиентами; новые ходят в `/notifications`
  (ниже) — тот отдаёт ту же ленту вместе с приглашениями и счётчиком. Когда старые
  версии вымрут, `/activity` следует убрать.

### Раздел «Уведомления»

- `GET /api/v1/notifications?limit=30&offset=0` →
  `{"invites": [InviteCard], "items": [ActivityItem], "unreadCount": 0, "seenThrough": "…"}`.
  `items` и правила пагинации — те же, что у `/activity`.
  `invites` — закреплённые сверху карточки: `pending` (ждут его согласия) показываются
  всегда, `added` (человека добавили) — **только пока не просмотрены**, то есть пока
  `createdAt` карточки новее отметки прочитанного; `left` и `declined` не показываются
  никогда.
  Статус карточки берётся из **комнаты**, а не из хранимой записи: участнику карточка
  всегда отдаётся как `added` (выбор «Принять/Отклонить» для группы, где он состоит, сам
  себе противоречит), а не-участнику `added`-карточка не показывается вовсе — она
  протухла, вести по ней некуда. Если комнату прочитать не удалось, отдаётся хранимый
  статус: сбой чтения не должен гасить живые карточки.
  `unreadCount` считает непрочитанные события ленты **по всей ленте, а не по отданной
  странице** (иначе запрос бейджа с `limit=1` всегда давал бы «1»), плюс каждую
  показанную карточку приглашения — включая `added`, а не только `pending`: человека
  добавили молча, и он должен об этом узнать. `pending` держит счётчик ≥ 1, сколько бы
  раз раздел ни открывали, — карточка требует решения.
  В счёт идут **только те события, которые человеку адресованы**: раздел — входящие, а не
  журнал. Источник правды — поле операции `notification_sent`, список **адресатов**
  уведомления по ней. Пишет его **только REST-нотификатор** (точечный `$set` из фоновой
  рассылки): бот копит такой же список локально, но лишь чтобы не отправить одному
  человеку два сообщения — записать его в базу дёшево нельзя, он собирается под гейтами
  telegram-канала и означал бы «у кого есть телеграм», а получатель из приложения молча
  выпал бы из бейджа. По той же причине список пополняется **до** проверки настроек
  доставки: выключенный push или telegram гасит сообщение, но не входящие — иначе человек
  без push-разрешения и без телеграма (вход через Google/Apple) не увидел бы бейдж
  никогда, а правило разошлось бы с фоллбэком по долям, никаких настроек не знающим.
  Отсюда для расходов, заведённых через REST: свой расход бейдж не
  поднимает, чужой без твоей доли — тоже, а расход, где тебя **назначили плательщиком**,
  поднимает: уведомление о нём уходит всегда. Пустой список означает не «никому», а
  «неизвестно» (легаси-операции эпохи бота, расходы, заведённые или отредактированные
  в боте, ещё не долетевшая фоновая рассылка) — для таких работает правило по долям:
  получатель с ненулевой долей и не плательщик. Правка расхода в боте — это новая запись
  с новой датой, и список у неё **обнуляется**: унаследованный описывал бы состав прошлой
  версии.
  Значение точное до **99**; **100** означает «больше 99» — клиент рисует «99+»
  (клампить ровно 99 нельзя: точное «99» неотличимо от потолка).
  `seenThrough` — **время формирования этого ответа**, снятое ДО чтения ленты: событие,
  созданное во время чтения, иначе оказалось бы старше отметки, не попав в ответ.
- `POST /api/v1/me/notifications-seen` — отметить прочитанным. Тело:
  `{"seenThrough": "…"}` → `204`.
  Клиент обязан вернуть `seenThrough` **из ответа**, а не своё локальное «сейчас»:
  событие, пришедшее между ответом и тапом, иначе погасло бы непоказанным.
  Отметка двигается только вперёд — приход более раннего значения ничего не меняет.
  `400 validation` — если `seenThrough` отсутствует/нулевой или уходит в будущее дальше
  чем на минуту (кривые часы клиента).
  Состояние прочитанного — одна отметка на пользователя (`users.notifications_seen_at`),
  а не флаг на каждом событии.

### Настройки уведомлений

- `GET /api/v1/me/notifications` → по категории на канал доставки:
  `{"operations": {"telegram": true, "push": true}, "debts": {…}, "invites": {…}}`.
  Незаданная категория считается включённой, но **мастер-выключатель сильнее матрицы**:
  при `notificationOn: false` (`PATCH /me`) выключены все категории и оба канала,
  независимо от того, что в матрице.
- `PATCH /api/v1/me/notifications` — частичное обновление: приходят только меняемые поля,
  ответ `200` с новой действующей матрицей.
  Патч накладывается на **действующие** значения, поэтому тело старого клиента (без
  `invites`) эту категорию не выключает.

Категория `invites` управляет уведомлением о приглашении ровно так же, как `operations`
и `debts` — своими событиями. В push-payload она едет как `data["channel"] = "invites"`;
**сервер** кладёт это значение в `AndroidNotification.ChannelID` (`internal/push/push.go`),
поэтому канал с таким id обязан существовать в приложении — фоновое уведомление рисует
система, и на Android 8+ уведомление с неизвестным каналом не показывается молча.
В форграунде приложение маппит значение само и неизвестное сводит к `operations`.

### Статистика

- `GET /api/v1/rooms/{roomId}/statistics` → `Statistics` — расширенная статистика для дашборда.
  Считаются **только активные расходы** (погашения и черновики исключены), легаси-операции —
  через существующую нормализацию (`normalizedRoom`), доли получателей — канонические целые.
  - `currency` — валюта комнаты (пустая в базе → `RUB`);
  - `totalSpent` — сумма всех расходов комнаты;
  - `operationCount` — число всех расходов комнаты за всё время (погашения и черновики не считаются);
  - `monthSpent` — расходы текущего календарного месяца (по `create_at`);
  - `byDay` — траты по дням за последние 30 календарных дней (включая сегодня):
    только дни с тратами, ISO-дата `yyyy-mm-dd`, по возрастанию даты;
  - `byMonth` — траты по календарным месяцам за последние 6 месяцев (включая текущий):
    ровно 6 элементов, месяцы без трат присутствуют с `sum: 0`, формат `yyyy-mm`,
    по возрастанию месяца (по `create_at`);
  - `paidByMember` — кто сколько заплатил (доноры расходов), по убыванию суммы;
  - `shareByMember` — чья доля потребления (получатели с их долями), по убыванию суммы;
  - `topOperations` — топ-5 расходов по сумме (`id`, `description`, `sum`, `donor`, `createdAt`).

### Файлы (чеки/фото из Telegram)

- `GET /api/v1/files/{fileId}` — проксирует файл из Telegram (`getFile` + download по `file_path`).
  Доступ: аутентифицированный пользователь, у которого есть комната с операцией, содержащей этот `fileId` (`403` иначе).
  `503 unavailable` если бот не сконфигурирован.
- `GET /api/v1/users/{userId}/avatar` — проксирует аватар пользователя из Telegram
  (`getUserProfilePhotos` + download), кеш на сутки.
  ⚠️ `{userId}` — **номер Splitty** (`_id`), а не telegram id: сервер сам достаёт `telegram_id`
  из документа. `404 not_found`, если пользователя нет **или у него нет `telegram_id`** (вход
  через Google/Apple, dev-вход) — клиенты в этом случае рисуют инициалы.
  `503 unavailable` если бот не сконфигурирован.

### Диплинк-вход в группу (публичные маршруты, без `/api/v1`)

Три маршрута регистрируются **намеренно без авторизации**: `.well-known`-файлы читают
операционные системы, а страницу приглашения открывает браузер человека, у которого аккаунта
ещё может не быть — ради него диплинк и делается. Все три выключены, пока пуст `PUBLIC_BASE_URL`
(тогда `404`).

- `GET /.well-known/apple-app-site-association` → `200`, `Content-Type: application/json` —
  файл, по которому iOS связывает домен с приложением. Формат современный (`applinks.details`
  с `appIDs` + `components`), путь — `/join/*`. `404`, если пуст `IOS_APP_ID`.
  ⚠️ Отдавать обязательно **по HTTPS и без редиректов**: iOS скачивает файл через CDN Apple и
  молча отвергает и редирект, и чужой `Content-Type`.
- `GET /.well-known/assetlinks.json` → `200`, `Content-Type: application/json` — Digital Asset
  Links для верификации app links Android (`autoVerify`). `404`, если пуст `ANDROID_PACKAGE`
  или `ANDROID_CERT_SHA256`.
- `GET /join/{roomId}` → `200` HTML — страница приглашения. Отдаёт **только название группы и
  код приглашения** (код = `roomId`), кнопку «Открыть в приложении» (`splitty://join/<roomId>`)
  и ссылки на сторы. Ни участников, ни сумм, ни операций: ссылку пересылают в чаты.
  ⚠️ **Смотрящего здесь нет и проверки членства тоже: знание `roomId` И ЕСТЬ приглашение.**
  Страница отдаёт название любому, кто держит валидный ObjectID — иначе ссылка не работала бы
  для приглашаемого, которого в комнате по определению ещё нет. Неразличимы только мусорный id
  и несуществующая комната: оба дают нейтральное «Приглашение не найдено» (`404` с той же
  страницей). Ошибка базы — третий исход: `500` со страницей «Что-то пошло не так» (ложное
  «ссылка протухла» отправило бы человека просить новую).
  Заголовки: `X-Robots-Tag: noindex`, `Cache-Control: no-store`.
  `429 rate_limited` при более чем 60 открытиях с адреса в минуту (свой бюджет: за одним NAT
  сидит целая сеть, куда ссылку и переслали).

**Кто производит такие ссылки.** Сервер: `GET /api/v1/rooms/{roomId}` отдаёт поле
`inviteUrl` = `<PUBLIC_BASE_URL>/join/<roomId>`. Пока `PUBLIC_BASE_URL` пуст, поля нет вовсе, и
клиенты показывают старую ссылку через telegram-бота (`https://t.me/split_money_bot?start=room<id>`).
Оба формата принимаются парсерами кода приглашения на обоих клиентах.

Собственно вступление в группу делает уже авторизованный клиент — `POST /api/v1/rooms/{roomId}/join`.

### Служебное

- `GET /health` → `200 {"status":"ok"}` (без авторизации).

## Замечания по реализации

- Роутинг: stdlib `net/http` + `http.ServeMux` c паттернами методов (Go ≥1.22).
- JWT: `github.com/golang-jwt/jwt/v5`.
- **Авторизация — обязанность REST-слоя**: членство в комнате и авторство операции проверять в хендлерах (в сервисах проверок нет).
- Долги считать расчётом develop — `service.GetRoomDebts` — по **нормализованной копии**
  комнаты (`internal/rest`: `normalizedRoom`): легаси-операции получают синтезированные
  канонические доли, драфты/архив исключаются; база не мутируется. Алгоритм не дублировать.
- Каноническое правило деления — `api.ShareOf` (`internal/api/money.go`), общее для
  создания операций, отдачи DTO и синтеза легаси-долей.
- Все хендлеры — тонкие: парсинг → проверки прав → вызов сервиса → маппинг в DTO.
