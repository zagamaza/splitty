# Приглашение друга уведомлением + раздел «Уведомления»

> **Ревизия 3** — самопроверка после двух кругов.
> Найдено в собственной правке ревизии 2: предложенный «атомарный выход» фильтром в mongo **пропустил бы легаси-операции** (`normalizedOperation` синтезирует `recipients_with_sum` в памяти, в базе их нет) — человек со старыми долгами смог бы выйти; у карточки «вас добавили» не было выхода, кроме как через настройки группы; примирение после сбоя указывало на неверный шаг; не учтён случай «человек — плательщик», где убрать себя из получателей недостаточно; `/friends` может содержать удалённых, приглашение которых вернёт 404.
>
> **Ревизия 2** — после двух кругов ревью (Fable + Codex), проведённых параллельно.
> Исправлено: `/friends` строится из текущих участников, из-за чего повторное приглашение вышедшего было недостижимо; push в Task 3 опирался на механику из Task 8; починка ключа пуша на iOS ничего не чинила (у события нет подписчиков); `/join` не примирял запись приглашения; check-then-act гонки при выходе и смене статуса; отметка прочитанного стирала непоказанное; `unreadCount` не считал непрочитанные `added`; на Android отсутствовал канал `invites` (пуш молча не показался бы) и маршрут `NOTIFICATIONS` уже занят настройками; «архивная комната» — несуществующее понятие (архив персональный).

## Overview

Сегодня попасть в группу можно только самому: ввести код в шите «Присоединиться» (`GroupsListView.swift:33`) или пройти по ссылке. Человек, которого позвали, должен сам найти код и его ввести — это не индустриальная практика. У Splitwise кнопки «присоединиться» нет вовсе: «You cannot join a group on your own — a current member of the group will need to invite you».

Меняем на входящее событие: **участник зовёт друга, тому прилетает push и карточка в приложении**. Друг из `/friends` — это человек, с которым уже была общая группа, значит его `_id` известен, и добавить его можно сразу, без ввода кодов.

Заодно вкладка «Активность» становится разделом **«Уведомления»**: она уже рендерит человеческие фразы («Вася добавил(а) „Ужин" в группе „Поездка"»), ей не хватает бейджа, отметки непрочитанного и закреплённых действий.

И — обязательная часть, без которой первое становится ловушкой: **выход из группы** и **удаление участника**, которых сегодня нет в REST вовсе.

### Принятые решения (не пересматривать при исполнении)

1. **Друга из `/friends` добавляем сразу**, без запроса согласия — id уже есть; ему уходит push и карточка «вас добавили».
2. **Посторонним — существующая ссылка** `/join/{roomId}`. Ничего нового не строим.
3. **Placeholder-участники и приглашения по email — НЕ делаем.** Первое требует слияния аккаунтов и переписывания id в снимках (запрещено инвариантом), второе — отправки писем, которой в проекте нет вообще.
4. **Выход запрещён, если на человеке есть операции.** Это честно к кредитору и НЕ ловушка: правка и удаление расхода доступны **любому участнику** (`handlers.go:864`, `:947`), поэтому человек может убрать себя из операции сам, а затем выйти.
5. **После выхода повторное добавление — только с явным согласием** (иначе цикл «убрал себя → вышел → добавили снова»).
6. **Удаление участника доступно** — для того, кто позвал не того.
7. **«Активность» → «Уведомления»**, иконка-колокол, бейдж непрочитанного.
8. **Приглашения храним** отдельной коллекцией; **ленту событий выводим на лету**, как сейчас (никакого fan-out строк на каждый расход).
9. **Прочитанность — одна серверная отметка** `notifications_seen_at` на пользователе.
10. **Новая коллекция обязана попасть в `purgeUserData`** при удалении аккаунта.

## Solution Overview

### Модель приглашения

Одна запись на пару «комната × приглашённый», хранящая **текущее состояние отношения**:

```
room_invite {
  _id, room_id, invitee_id, inviter_id, created_at, status, seen_at
}
```

`status`:
- **`added`** — друга добавили сразу (основной путь). Он уже участник; карточка информационная, гаснет после просмотра;
- **`left`** — человек вышел из группы. Тихо добавить его снова нельзя;
- **`pending`** — повторное приглашение после выхода; участником **не** делает, ждёт решения;
- **`declined`** — отказался вернуться.

Уникальный индекс `(room_id, invitee_id)`, запись обновляется upsert-ом.

### Потоки

**Позвать друга (первый раз):** проверяем, что зовущий — участник, а приглашаемый есть в `/friends` → `JoinToRoom` → запись `added` → push.

**Выйти:** если на человеке есть операции (донор или получатель) → `409` с внятным текстом «уберите себя из расходов». Иначе `LeaveRoom` → запись `left`.

**Удалить участника:** те же правила, что для выхода (нельзя удалить того, на ком висят операции) → `LeaveRoom` → `left`.

**Позвать повторно (был `left`/`declined`):** запись `pending`, участником не делаем, push «приглашает вас вернуться». Принять → `JoinToRoom` + `added`. Отклонить → `declined`.

### Раздел «Уведомления»

`GET /api/v1/notifications` отдаёт:
- **закреплённые** — приглашения: `pending` (всегда, требуют решения) и `added`, у которых `created_at > user.notifications_seen_at`;
- **ленту** — то же, что сегодня отдаёт `/activity` (обход комнат на лету, без хранения);
- **счётчик непрочитанного** — количество `pending` + число событий новее `notifications_seen_at`.

`POST /api/v1/me/notifications-seen` двигает отметку. Прочитанность одна на пользователя и живёт на сервере — синхронна между устройствами; цена — нельзя вернуть отдельное событие в «непрочитано» (принято осознанно).

### Категория уведомлений

Приглашения — **новая категория `invites`** рядом с `operations`/`debts` (`tg.go:203`), по умолчанию включена. Мастер-выключатель `NotificationOn` действует и на неё. **Карточка в разделе появляется независимо от настроек** — настройки управляют доставкой (push/telegram), а не наличием записи.
