# Контракт продуктовых событий

Единственный источник правды об именах событий и их параметрах. Его читают три
стороны: iOS, Android и белый список на сервере. Имя события — проводной
контракт: опечатка ничего не роняет, она молча уводит шаг воронки в никуда, и
видно это будет только по неправильному числу через месяц.

**Порядок изменений: сначала сюда, потом в код.** Контракт-тест на сервере
читает этот файл и сверяет с белым списком; разошлись — тест красный.

## Общие поля

Каждое событие несёт:

| поле | что это |
|---|---|
| `id` | идентификатор события, генерирует клиент. Обязателен и непуст, формат как у `clientOpId`: до 64 символов из `[A-Za-z0-9-]`. По нему идёт дедуп |
| `name` | имя события из таблицы ниже |
| `at` | когда случилось, RFC3339. Сервер зажимает в окно «не старше 7 суток, не позже часа вперёд», иначе подставляет время приёма |
| `session` | идентификатор сессии, тот же формат что у `id` |
| `platform` | `ios` или `android` |
| `app_version` | версия приложения **на момент события** |
| `locale` | код языка интерфейса |
| `params` | параметры события; ключи и значения — только из таблицы |

**Свободного текста, сумм и имён в параметрах не бывает.** Ни названия тусы, ни
описания расхода, ни суммы. Только закрытые множества — иначе агрегаты нельзя
группировать, а событие превращается в утечку.

### `app_version` — версия события, а не отправки

Заголовок `X-Client-Version` (его шлют оба клиента) — это версия, которая
**отправляет** пакет. Событие могло случиться до обновления и пролежать в
очереди. Обе величины осмысленны, путать нельзя.

Отдельно: заголовок несёт продуктовый смысл — по его отсутствию выдаётся
`AI_LEGACY_DAILY_QUOTA` (`docs/API.md`). Поле события **с квотами не связано**,
и сводить их нельзя.

### Ротация `session`

Новая сессия начинается:

- на холодном старте приложения;
- после возврата из фона, если в фоне провели больше 30 минут.

Одинаково на обеих платформах. От этого зависит смысл любой
последовательности шагов: разъедется правило — разъедется и порядок событий.

## События

| событие | когда стреляет | параметры |
|---|---|---|
| `app_open` | запуск и возврат из фона | `cold`: `true` / `false` |
| `login_completed` | успешный вход | `method`: `telegram` / `google` / `apple` / `password` / `code` / `dev` |
| `onboarding_started` | показан первый экран приветствия | — |
| `onboarding_step` | пролистан экран приветствия | `step`: `group` / `dictate` / `who_paid` / `transfers` |
| `onboarding_completed` | нажата «Создать группу» на последнем экране | — |
| `onboarding_skipped` | приветствие закрыто, не дойдя до конца | — |
| `room_created` | туса создана | — |
| `room_joined` | вход в тусу удался | `via`: `link` / `code` / `invite` |
| `room_join_failed` | войти в тусу не удалось | `reason`: `not_found` / `deleted` / `forbidden` / `network` |
| `expense_added` | расход добавлен | `method`: `manual` / `voice` / `receipt` |
| `expense_parse_failed` | распознавание не удалось | `reason`: `quota` / `rate_limited` / `unsupported_media` / `too_large` / `validation` / `network` / `internal` |
| `settle_up_opened` | открыт расчёт долгов | — |
| `settle_up_done` | долг отмечен погашенным | — |
| `paywall_shown` | показан экран оплаты | `from`: `quota` / `account` |
| `paywall_dismissed` | экран оплаты закрыт без покупки | `from`: `quota` / `account` |
| `purchase_started` | нажата покупка | `product`: `monthly` / `yearly` |
| `purchase_completed` | покупка прошла | `product`: `monthly` / `yearly` |
| `purchase_failed` | покупка не прошла | `reason`: `cancelled` / `store` / `verify` / `network` |
| `invite_sent` | приглашение отправлено | `channel`: `link` / `share` |

`screen_view` **зарезервирован и вводится в V2** — вместе с закрытым списком
имён экранов и своим контракт-тестом. Это самая большая клиентская поверхность
набора (каждый экран на двух платформах), а ни один блок первой версии без него
не ломается. Причина отложить — трудозатраты, не объём данных.

## Почему набор именно такой

Считать проценты на 267 пользователях и четырёх живых группах в неделю
бессмысленно: это единицы наблюдений, шум, который выглядит как сигнал. Поэтому
экранов воронки и удержания в первой версии нет.

**Но «не показывать метрику» и «не собрать границы шага» — разные вещи.** Не
собранное вчера завтра не появится. Поэтому три пары «показ → попытка → исход»
заведены сразу, хотя считать по ним пока никто не будет:

- **онбординг**: `started` → `step` → `completed` / `skipped`. Без `started` шаги
  двусмысленны: непонятно, сколько человек вообще дошло до первого экрана.
- **покупка**: `paywall_shown` → `purchase_started` → `completed` / `failed`, и
  отдельно `paywall_dismissed`. Без `purchase_started` обрыв на экране оплаты
  неотличим от отказа магазина. `paywall_dismissed` заведён явно, а не выводится
  как «показ без начатой покупки»: такая производная склеивает «закрыл экран» и
  «ушёл из приложения», а это разные ответы на вопрос «почему не купили».
- **вход в тусу**: `room_joined` / `room_join_failed`. Вход по ссылке — известное
  место обрыва, и неудача там происходит уже под авторизацией, то есть собираема.

**`room_create_failed` не заводится.** Создание тусы — локальная форма и один
вызов; отказ там сетевой и попадёт в общий счёт ошибок. Отдельное событие было
бы дублем, а не границей шага.

**Воронка входа объявлена вне scope.** Приём событий закрыт авторизацией, а
неудачная попытка входа по определению происходит до неё. Знаменателя у
`login_completed` не будет, и делать вид, что будет, не надо.

**Числа Apple и этот поток не склеиваются в одну воронку.** Показы и просмотры
страницы в App Store — обезличенные и до установки, наши события — после входа и
с человеком. Это соседние числа, а не верх и низ одной когорты.
